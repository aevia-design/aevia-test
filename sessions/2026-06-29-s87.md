**Shipped LIVE: the Wander cover edge-sliver fix. One commit on `main` (`f695f97`), pushed → Cloudflare deploying. The fix took three diagnostic passes; `/systematic-debugging` (with live-DOM Playwright inspection) found the true root cause after two wrong guesses.**

## What happened

Continued S86's open item: a dark sliver on the Wander cover edges in the staff engine + customer preview. S86 had fixed the back/spine **background fill** colours (navy → maroon/green) but a dark line remained on the front-cover **right edge** (and spine top/bottom).

### The debugging journey (3 passes)
1. **Wrong guess #1 — the page frame.** Assumed the `.cover-canvas` `border` + `box-shadow` (added S79 for pale templates) was the dark outline. Added `border-color: transparent; box-shadow: none`. Evgeny: no change.
2. **Wrong guess #2 — front bg colour.** Noticed `sections.front.bgColor` was still cream `#f2ede3` while the real board is `#E7DED3` (per `mockupEdges.front`). Changed it. Still no change.
3. **`/systematic-debugging` + live Playwright DOM inspection (the real RCA).** Evgeny supplied a no-auth customer-preview token URL, so I drove the **live** page headless (`@playwright/test`, already a dep) and pixel-sampled the rendered edges:
   - The dark line is exactly **1px**, colour `45,41,97` (navy) = the canvas **background gradient**.
   - Hiding the SVG → line persisted (not artwork). Removing border-colour + box-shadow → line persisted (not those).
   - Setting `background: red` → the line turned **red** ⇒ it's the background bleeding through.
   - With the fixed maroon/green colours the line became **maroon** (the *back* colour) regardless of front colour ⇒ the 1px sliver shows under the border because `background-clip` defaults to **border-box**, painting the gradient beneath the 1px page-frame border. That's why front-colour changes did nothing, and why `border-color: transparent` failed (the transparent border box still existed, gradient still bled through it).
   - `background-clip: padding-box` → **0 dark edge pixels**, clean greige to the edge with a tidy light-grey hairline (the look Evgeny wanted).
4. **Second root cause (why localhost still failed after the CSS fix).** The gradient is set in JS via `canvas.style.background = …`. The `background` **shorthand resets `background-clip` to border-box inline**, and inline beats the stylesheet rule. So the CSS `background-clip: padding-box` never applied. **Fix: set `canvas.style.backgroundClip = 'padding-box'` inline, immediately after the shorthand**, in both engines. Evgeny confirmed it works.

## ⚠ Watch-outs (S87)
- **The `background` shorthand resets `background-clip`.** Any future cover-background change via `canvas.style.background = …` must re-set `backgroundClip = 'padding-box'` after it, or the edge sliver returns. This is the actual gotcha, not the colour values.
- **Cover edge slivers are a general pattern**, not Wander-specific: any template whose cover background is darker than the page will show the same 1px sliver if the padding-box clip is dropped. The fix lives in the shared render path, so all templates benefit.
