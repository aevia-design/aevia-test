## The core finding: the 2026-07-13 brief was written without looking at the live DNS

It guessed. Everything below was verified this session (DNS-over-HTTPS — note **`dig` is not installed** on this box; use `curl -s -H 'accept: application/dns-json' "https://cloudflare-dns.com/dns-query?name=X&type=Y"`).

**The live zone:** nameservers `ns1–ns4.helloly.com` (registrar = DNS host, one place). **DNSSEC OFF** — the single biggest silent-killer in a nameserver move, and we're not exposed to it. **No CAA record** (a restrictive one would have silently blocked Cloudflare's cert). MX → M365. SPF `-all`, M365-only. Brevo DKIM (`brevo1/brevo2._domainkey`) + `brevo-code` TXT both live → **Brevo domain auth is DONE** (S107), don't re-do it. DMARC `p=none`. Apex + www → helloly parking IP (the only records we replace). 14 plausible M365/Brevo hostnames + 3 SRV names probed and absent; no wildcard; CT logs empty.

**Two pre-existing quirks, deliberately NOT touched during migration** (they work; changing them mid-cutover would confound a mail failure): Brevo is not in SPF (its mail passes on DKIM alignment alone), and M365 DKIM is not configured (Xenia's outbound passes on SPF alone).

## Then a critic tore up my correction, and found four more errors

Owner asked for an independent `/critic` pass. It re-queried DNS itself, probed the live deploy, and read `firestore.rules`. It found **four load-bearing errors in my v1**:

1. **I said a server-side per-host gate was impossible. It isn't.** Becoming a Cloudflare *zone* — which the apex requirement forces anyway — unlocks **Redirect Rules** (Free plan): per-host, at the edge. My client-side JS gate **fails open** — if `site-mode.js` 404s or throws, the order form renders in full on the live domain, i.e. exactly the risk being defended against. Rule is now primary, JS is the belt.
2. **"We never need to roll back" was false.** After the NS flip there is a **split-brain window** of hours — some resolvers still read helloly, some read Cloudflare. A record "fixed in 60s" at Cloudflare is invisible to the rest. **Consequence: leave the helloly zone intact for a week.** Don't tidy up. That urge is itself a mail-outage vector, and the plan's own framing created it.
3. **The single `SITE_URL` constant would break the test rig.** `functions/index.js:878` feeds Stripe's `success_url`/`cancel_url` — a flat constant means a `pages.dev` test order goes to Stripe and lands on the *live* domain mid-checkout. Fixed: derive per-request from an origin allowlist.
4. **I scaremongered about a service-account key leak.** `functions/serviceAccountKey.json` is gitignored — it isn't in the repo Cloudflare deploys from. The `/functions/` conclusion stands, on better grounds.

It also found **`robots.txt` already exists** — Cloudflare auto-injects a "Content Signals Policy" file making AI-licensing statements on Aevia's behalf that nobody here has read. Both earlier documents said there was none.

## Security: the migration cannot open a hole

Checked directly. Every Cloud Function sets `Access-Control-Allow-Origin: *` (~23 occurrences). `firestore.rules` has **no host/origin logic** — `/orders/{orderId}` is `create, delete: if false`, so customers cannot write orders from the browser at all; every customer flow goes through a Cloud Function on the admin SDK. **Authorisation is 100% bearer-credential** (Firebase ID token, preview UUID, Stripe webhook signature).

- **Adding `aevia.at` to a CORS allowlist buys nothing.** Nobody should "harden CORS" and think they've secured something.
- **Preview tokens are not host-bound** (`functions/index.js:139-146`) → **in-flight preview links survive the migration.** Real non-risk, worth stating.
- **The order gate is a courtesy, not a lock** — a direct POST to a function URL bypasses it regardless of host. Fine pre-launch; do NOT add App Check for this.
- Pre-existing (not caused by this): `functions/upload.js:4` allows `/\.pages\.dev$/` + `/\.webflow\.io$/` **unanchored** → any pages.dev project matches. Harmless (CORS isn't a control here); clean up while in the file.
- **`/security-review` timing: NOT now** (no diff to review). Run it at the end of Phase 5 — the per-request origin allowlist is the one genuinely review-worthy change.

## Owner decisions taken

- **Migrate now, gate the order flow.** NOT for an SEO head start (that argument is weak and we explicitly do not rely on it) — but because transactional emails bake the hostname in permanently, and because the dangerous DNS hour should happen with nothing at stake.
- **Homepage = `aevia.at/`** (owner: "yes, aevia.at shall be homepage"). `_redirects` changes from `/ /pages/home.html 301` to a **200 rewrite** — verified supported by Cloudflare Pages. Today the homepage costs two hops. Decided now because Phase 5 bakes URLs into emails.
- **Waitlist = a Brevo hosted form on a static page.** Not a Cloud Function + Firestore collection (v1 proposed that; it was scope creep, and its "a callable isn't a spam target" rationale was simply wrong). Brevo is already in the stack and brings double opt-in, consent capture and unsubscribe — which we need anyway for EU addresses.
- **Copy:** avoid "beta" (software register, wrong for a craft brand) and avoid a hard launch date (a stranger can screenshot a promise). "Opening this autumn."
- **SEO splits by content-dependence.** Content-independent work (canonicals, real `robots.txt`, Search Console, the URL decision) ships with the migration because it gets *more* expensive to defer. Content-dependent work (meta descriptions, OG, schema, sitemap) waits for Xenia's copy + the photography, ~Sep.

## Watch-outs for the executing session

- **`/functions/` is off limits to Cloudflare.** It's the Firebase source, and Pages auto-detects a root `/functions/` dir as Pages Functions. Verified live: `/functions/email.js` → **404**, `/package.json` → **200** — Pages already excludes it. The build only survives because nothing in there exports a handler in the shape Pages looks for. Adding `_middleware.js` would be the first one.
- **Do NOT enable Cloudflare Email Routing.** Prominent in a new-zone dashboard, sounds helpful, **rewrites your MX records** — a one-click outage on a zone carrying live M365 mail.
- **Grey vs orange:** mail records DNS-only (grey); the Pages web records **are** proxied (orange) and that's correct. "All grey" would break the site.
- **Arrival is not the mail test.** With DMARC `p=none`, mail with broken DKIM/SPF still *arrives* — it just quietly starts landing in spam and you find out weeks later. Test the **`Authentication-Results` header** (Gmail → Show original → SPF/DKIM/DMARC all PASS), on both a Brevo transactional mail and a message from Xenia's M365 box.
- **Enumerate the zone from the registrar export, not from DNS queries.** DNS cannot be listed from outside — a record nobody thought to query looks identical to one that doesn't exist. helloly export is the source of truth; M365 admin + Brevo domain page are the cross-checks; Cloudflare's auto-scan has the *same* blind spot (it guesses common names) so don't trust it either.
