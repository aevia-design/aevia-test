### 11:00 — The Geoapify "leaked secret" email is real but misframed

**Done:** Tested the live key four ways and swept the repo and full history for other secrets.

**Decided:** No code change. The key stays public in `pages/account.html:279`; rotation is optional
hygiene, and the owner's call was to park it.

**Why:** It is a **browser** key — the address autocomplete runs client-side, so every visitor
already has it and GitHub is not the exposure. The domain restriction works: a forged referrer gets
**401**, `aevia.at` gets 200. The scanner's "still valid" is a request with **no Referer header at
all**, which returns 200 — and that hole cannot be closed while the key lives in a browser, because
the referrer is client-supplied. Google Maps keys have the identical property.

**Watch out for:** Worst case is **quota theft**, not data loss — the key only geocodes, touches no
Firestore, and the account has no card. Draining the 3,000/day free tier would silently kill
autocomplete, but the manual address fields still work (progressive enhancement), so no customer is
blocked. **Before treating a recurrence as urgent, look at the Geoapify usage graph** — that is the
only thing separating "theoretical" from "happening".

**Also confirmed:** the key appears in exactly one file and one commit (`653e492`). No `.env`,
`serviceAccountKey.json`, private key or Stripe `sk_` has ever been committed on any branch. The two
grep hits (`ROADMAP.md`, `sessions/2026-06-01.md`) are prose, not keys.
