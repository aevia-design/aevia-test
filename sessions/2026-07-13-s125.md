### Promo decisions via /solutioning → ADR-0008
**Decided (owner):** (1) F&F codes = **unique per-person codes** generated in Stripe, not a
shared FRIENDS30 — so redemptions are traceable per person and there's no shared code to
misconfigure. (2) Self-referral = **hard-deny** (F-P1-03), not just cap.
**Decided (approach):** Move promo-code entry from Stripe's hosted field onto Aevia's pay page:
a "Have a code?" field → `validatePromoCode` (asks Stripe if the code is valid + does the ONE
check Stripe can't: reject if the code's owner email == buyer email, via the existing
`referralCodes/{id}` index) → pre-apply the valid code to the session (`discounts:[…]`) and set
`allow_promotion_codes:false`.
**Why:** Stripe has no per-customer denylist, so the block MUST live in our code upstream of
checkout. Same field also unifies validation for the unique F&F codes.
**Watch out for:** This is NOT a promo store — code creation, caps, expiry, redemption tracking,
and enforcement ALL stay in Stripe (managed via the Stripe Dashboard). The only Aevia-side data
is the owner-email index that already exists (S115). New maintenance = one validation Cloud Fn in
the money path. Build is money-path-sensitive → own focused session + regression test (plain
order / valid referral / self-referral attempt). Cap-now (coupon max_redemptions+expiry, zero
code) is the recorded interim fallback if the build slips. Full record: `docs/decisions/0008-*`.
