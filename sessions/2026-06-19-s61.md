## 1. UNBLOCKED Wander AEV-040 (the 3-session headless hang) — SOLVED

Root cause was **total image payload size**, NOT photo count / network / concurrency / HTTP2.
Evgeny's clue cracked it: Newborn AEV-039 = ~200 MB of low-res photos (sailed through);
Wander AEV-040 = ~2 GB of full-res originals. Headless Chromium silently STALLS a few in-page
`fetch().blob()` reads when it can't hold ~2 GB of decoded images in memory — `load-progress`
froze a few short of 52 (49–50/52) and `loadOrderIntoEngine`'s `Promise.all` then hangs forever
(panel never shows). A `page.route` Node refetch proved the network was fine (`52 ok, 0 gave up`)
— the renderer still has to hold it all.

**FIX (both capture scripts):** intercept `**/storage.googleapis.com/**` in the Node route and
**downsample each photo with `sharp` to ≤1600px JPEG before the browser sees it** (~2 GB → ~150 MB).
Mockups display a few hundred px wide so full-res is waste. `sharp` resolved via
`createRequire(path.resolve('scripts/package.json'))` (it lives in `scripts/`, not repo root).
Non-image/HEIC bodies pass through untouched. **Engine UNTOUCHED** → no parity concern.
- Files: `qa/capture-spread.mjs`, `qa/capture-cover-wrap.mjs` (both now: route + downsample +
  `routedShrunk` counter + the diagnostic line printed in `finally` so it shows on a timeout too).
- 6 prior fixes ruled out across s59–s61 (concurrency, deviceScaleFactor, HTTP/2, page.route
  retry, route streaming-vs-buffer, in-page throttle). LESSON: **ask about INPUT SIZE before
  theorising on a headless hang.**
- Result: AEV-040 = 22 mockups in `mockups/AEV-040/` (gitignored). FP1 Travel-map = `open-11-fp1`.
