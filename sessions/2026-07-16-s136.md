## 1 — CSV sync: captions + functional panels (`64f0b09`)
The coords had synced; the **font size had not**. `sync-joyride-csv.mjs` only ever pushed the six
photo-geometry fields, by design.
- **Audited every CSV column before extending anything** (throwaway script). Only captions were
  genuinely out of sync (the 10 rows). Everything else — bgColor, caption positions, alignment,
  font, colour, spacing — already matched.
- **⚠ The `Aspect ratio` column is decorative and rotted.** Nothing reads it at runtime, so nothing
  forced it to stay correct; it now contradicts its **own width/height** on 23 of 38 slots (a
  200×200 square row reads `03:02`; a 107×80 horizontal reads `03:04`). The JS is the truth, derived
  by hand from w×h. **Not synced, not even reported** — 23 warnings a run would train you to ignore
  the audit. `Orientation` is read by nobody either. Owner chose to **keep both columns** (inert).
  ⚠ **If w/h is ever nudged, the JS `ratio` must be hand-updated** — the script won't.
- **`csv-to-template.js` (Scribble-only generator) DOES read `Aspect ratio`** — `ratio === '33:35'`
  sets `heartClip`, which is live at runtime. Deleting that column would silently turn Scribble's
  heart slot into a rectangle. This is why the columns weren't deleted.
- **Functional rows now sync.** They were skipped because their key columns **collided** — both
  Intro rows just said `Intro`, so no row could be aimed at one panel. Owner made `Syb-type` unique

- **Fixed a latent bug in the original script:** block offsets were computed once, then the file was
  rewritten in a loop — every write shifted the offsets after it. Geometry edits shift 1–2 chars and

## 2 — customer-preview layout (`8ef5a45`) — reported as 2 issues, was 4 bugs
Owner: disclaimer eats ~1/3 width on the right; preview left-of-centre and cut (Safari).
- **Root cause:** `.page-body.preview-mode` is `display:flex` and inherited the default **row**
  direction. Its children are the canvas *and* the quality-note `<p>` → side-by-side columns. Note
  squeezed to **156px** (the clipped text) and the book pushed **78px** off-centre. **Not
  Safari-specific** — Chromium identical. Fix: `flex-direction: column`.
- **Inline styles beat the preview-mode rule** — the note kept `max-width:680px` when told
  `max-width:none`. Layout moved out of the `style` attribute; only `display` stays inline (JS owns it).
- **"Bottom" was impossible** — the bottom holds the flip pill (`bottom:88px`) and the fixed action
  bar, 17px apart. The note lands at y=872 in a 793-tall viewport. The only free band is **under the
  nav** — exactly where `.edit-hint` sits in edit mode (hidden in preview). Owner approved top.
- **`fitBook` scaled by WIDTH only** → a spread was a constant 600px tall whatever the window, so on
  a laptop-height screen its bottom slid under the action bar (the sliced caption in his screenshot).
  Added `previewHeightBudget()` — **preview only**; edit mode scrolls through every spread, so
  width-only is right there. Computed from **fixed chrome only**, never the spread's own rect
  (`justify-content:center` means scaling moves it → would chase its own tail).
- **⚠ `fitBook` early-returned on the hidden cover, for ever.** `if (!avail) { rAF(fitBook); return; }`
  guards the cover not being laid out yet — but preview renders ONE row, so off the cover its
  `clientWidth` is always 0. The spreads loop was **never reached** (a flipped-to spread kept its
  stale edit-mode scale) and **rAF looped at full tilt** burning CPU on every customer's machine.
  Now the cover branch is skipped when `offsetParent === null`.
- `updatePreviewMode()` didn't re-fit; cover now centres (margin auto + top-centre origin).
- **Verified on a REAL book (AEV-065)** in WebKit + Chromium at 1280×720 / 1431×793 / 1920×1080,
  cover + 3 spreads: nothing under the bar, note visible + full-width, spreads centred to **0px**
  (cover 12px — its 1227px vs the spreads' 1204px). Edit mode unchanged.

## 3 — PDF cover sub-labels silently missing (`45b186a`) — `/systematic-debugging`
Owner: Front/Spine labels printed; **both sub-labels absent** despite being saved in book state and
visible in both engines.
- **Root cause:** `drawCoverCaptions()` derived the font cut from a **numeric weight only** and never
  read `capDef.style`. Joyride's cover captions declare `style:'light'` with no weight → defaulted to
  400 → `'regular'` → asked for **`Mulish_regular`**. **Mulish is the ONLY family in `FONT_FILE_MAP`
  without a `_regular` cut** (Mulish-Light.ttf is the only Mulish file on disk), so `lookupFont`'s
  `|| ${font}_regular` fallback resolved to the **same missing key** → `null` → caller `continue`d
  with a `console.warn`. **Text silently dropped from a print-ready PDF.**
- `name`/`spine` survived only because `Lora_regular` exists — same wrong reasoning, luckier landing.
  The three **spread** caption paths already fell back to `capDef.style`, which is why Joyride's
  spread Mulish captions always printed and only the cover lost text.
- Fix: extracted `coverCaptionStyle()` (pure, exported) — explicit weight/italic wins (override
  first, then capDef, keeping Newborn's 500+italic → `mediumitalic`), else `capDef.style`, else
  regular. **TDD:** extracted unchanged first, confirmed the test **red** against real code (Joyride
  only, other 5 pass), then fixed.
- `tests/cover-caption-fonts.test.js` pins the **invariant**: every template's cover captions must
  resolve to a registered cut.
- **Preview/print parity confirmed:** Mulish-Light is the only Mulish cut on disk and the only
  `@font-face` either engine registers → the browser was already drawing Light.
- Logged **TO-DOS #77**: Papercut declares `weight: 'bold'` as a **string**; `'bold' >= 700` is
  `false` → its cover year prints regular. Cosmetic (Source Sans 3_bold IS registered, nothing
  vanishes) → deliberately not bundled.
