### Map "shifted & cut frame" = our CSS, NOT the artwork (the time-sink)
**Done:** Root cause = global `img { max-width:100% }` clamped the bleed-expanded
map overlay's WIDTH to the canvas but left inline HEIGHT alone → square PNG rendered
non-square + off-centre, breaking the symmetric 3mm crop. Fixed with
`max-width/max-height:none` on the map overlay in **order.html, template-engine.html,
customer-preview.html**. order.html also now scales off canvas `clientWidth` (excludes
its 1px border) → crop overhang equal on all 4 edges (2.78/2.78/2.80/2.80, measured).
**Decided:** Don't touch the bleed model / don't re-export maps.
**Why:** founder said the PNG looked evenly framed when opened directly → bug was in
render. A 30-sec DOM inspection (imgW 253 vs imgH 262 in 253 canvas) found it.
**Watch out for:** I wasted many turns measuring PNG pixels + wrote a re-export spec
(`docs/briefs/wander-map-reexport-spec.md`, now moot) + founder re-uploaded EU 3×, all
red herrings. LESSON (memory saved): for visual bugs, inspect live DOM geometry FIRST;
the brown-frame pixel detector gave FALSE asymmetry. Engine canvas has no border so it's
exact; PDF uses Sharp (no CSS) so unaffected.
