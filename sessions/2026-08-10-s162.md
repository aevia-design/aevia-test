### 11:15 — Every captured spread was blank: the picker wiped the captions
**Root cause:** `#monogram-select`'s change handler called `renderBook()` plainly, and
renderBook resets `window.bookCaptions` on a full rebuild. **This is the S161 bug at a
second call site** — and the one every mockup capture drives, via `qa/select-monogram.mjs`.
S161's guard only ever exercised the direct `renderBook({preserveCaptions:true})` call, so
the picker path was never tested. Opening an order by hand looked fine because the handler
only fires when a monogram is switched.
**Fix:** the handler passes `{ preserveCaptions: true }`. `qa/verify-order-text-seeding.mjs`
gained a picker scenario; it failed 3/3 before and passes 10/10 after.
**Also fixed:** each capture burned exactly 120s in select-monogram's post-monogram wait.
`'.cover-canvas img, .spread-pages img'` reads as "cover plus interior", but `.cover-canvas`
is built INSIDE a `.spread-pages` wrapper and renderBook makes one per spread — so it meant
all ~50 photos in the book, and one that never decodes leaves naturalWidth at 0 forever.
Scoped to `.cover-canvas`, 30s. Measured 120s → 1.3s.

### 13:40 — Green/Roses cover had no photo, and re-capturing could never fix it
**Root cause:** the Green Roses cover SVG carries a stray filled rect painted AFTER the
photo window — `x=758.859 y=104.971 w=238.259 h=248.855 fill="#dad0c5"`, against the
window's `x=771.028 y=113.464 226.772²  fill="none"`. Offset ~12mm left and ~8.5mm up and
not concentric, which is why the photo survived as a sliver on the right and a strip along
the bottom. `#dad0c5` is Beige's colour, foreign to a Green cover.
**Same class as the S157 filled-photo-window bug**, patched the same way: `fill="none"`.
Audited all 12 covers; this was the only one.
**Watch out for:** I first diagnosed it as a timing race and had the owner re-capture. An
identical result on the re-run is what ruled that out — random failures do not repeat
perfectly. **NOT mockup-only: the engine, customer-preview and the PDF all draw this file,
so a Green Roses book would have printed a blank square.** Re-apply on any Xenia re-export.

### 14:20 — Orders were not placed in colour order
**Watch out for:** the runbook assumed 089→beige, 090→brown, 091→green, 092→blue. Wrong.
Sampling each capture's cover background against the data files gives **beige AEV-089,
green AEV-090, blue AEV-091, brown AEV-092** — exact hex matches. Following the runbook
would have composed Brown's captures with Green's edge tints. `HEIRLOOM_ORDERS` in
`scripts/exp2-images.mjs` now records the mapping with the hex values.

### 18:10 — Breadcrumb: the text was centred, the strip was not visible
**Root cause:** the nav is `position:fixed` at 76.6px but `.crumb` reserved 69px, so the nav
covered the top 7.6px. My first fix centred the line box inside the crumb's own 45px box and
the owner still saw it high — because 7.6px of that box was never on screen.
**Watch out for:** box measurements said "centred" while the rendered pixels disagreed.
Screenshotting the element and finding the ink rows is what settled it. **At exactly 900px
the nav wraps to two rows (94.2px) and still buries 17px — pre-existing, affects every page,
needs a nav decision.** A residual 1.7px optical offset remains: all-caps has no descenders,
so a geometrically centred line box reads slightly high.
