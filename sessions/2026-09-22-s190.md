### ✅ TO-DOS #89 — `uploading` now becomes `upload_failed` by itself

**Built and DEPLOYED (`86d8c7c`).** The brief
(`docs/briefs/upload-failure-recovery.md`) had been READY TO IMPLEMENT since S174 with nothing
built. Pieces 1–7 are now live; **piece 0 (the Retry button) is deliberately not done** — it is
the one piece touching `pages/order.html` and needs the `qa:order` gate, so it gets its own
session.

**New: `functions/upload-failure-utils.js`** — pure decision logic, no Firebase, no SMTP. This
shape was chosen because `tests/chunk-4-order-flow.test.js` **copies** order-flow behaviour
instead of importing it, so it stays green whatever the handler does. The scheduled job calls
this module and the tests import the same one.

**New: `detectStrandedUploads`** (`functions/index.js`, appended) — hourly, `europe-west1`,
flips `uploading → upload_failed` past one hour. The flip is a **conditional transaction**, and
the customer email **re-reads `uploadComplete` immediately before sending**, so a tab that
retries successfully on the boundary cannot also be told it failed.

**`confirmUpload` now claims the confirmation in a transaction.** It was a read followed by an
update — a Retry racing a slow first call could have both read `uploadComplete: false` and both
sent mail. Both emails now run under `Promise.allSettled` with per-channel error fields, so one
SMTP failure cannot suppress the other. ⚠ **The guarantee is AT MOST ONCE and that is
deliberate** — Firestore and SMTP cannot be made atomic; a lost email is preferred to a duplicate.

**The staff "New Order" email moved from `createUploadSession` to `confirmUpload`**, so staff hear
about an order once it EXISTS. This also removed a live failure mode: an SMTP throw at creation
used to strand a new order **before the browser ever received its signed URLs**.
`createUploadSession` now emails nobody.

**Email normalised server-side at creation.** Not a live bug (the browser already lowercases it),
but the job matches orders by address and must not depend on the client behaving.

**Dashboard:** filter button, counts (as an **Issue**, not In progress), the `allStatuses`
dropdown, `statusLabel`, and a red disposition line on failed rows.

**`upload_failed` stays OUT of `STATUS_SEQUENCE`** — it is a side-state like `issue`. ⚠ The old
guard skipped itself whenever `indexOf` returned `-1`, **silently permitting any jump at all**;
unrecognised statuses now prompt instead of falling through.

**Two corrections to the brief, whose line numbers had gone stale:**
- `statusLabel` returns `labels[s] || s`, so an unmapped status renders the **raw string**. The
  brief's "falls back to Uploading" is true of the **dropdown** (`allStatuses`) — a different bug
  in a different place. Both fixed.
- `PRE_APPROVAL` (dashboard) and `PRE_APPROVAL_STATUSES` (`index.js`) are two status lists the
  brief never mentions. **Both already exclude `upload_failed` by omission, which is what the
  brief wants** ("not eligible for preview-send"). No change needed — do not "fix" them.

**Verified:** 657 tests green across 38 suites, **29 new** — 22 for the decision logic and 7
driving the **shipped `confirmUpload` handler** with mocked dependencies. That is the **first
import-based handler test in the repo** (`tests/confirm-upload-emails.test.js`); every other
test in this area simulates. Dashboard loaded in Chromium: module executed, new filter renders in

The two stale assertions in `chunk-4-order-flow.test.js` that documented the OLD flow were

### `delegating-to-codex` — the "headless = blackbox" worry was checked and is mostly wrong

Owner disliked headless delegation as opaque. Verified against `codex exec --help` on 0.146.0:
it **streams the full event log**, `--json` gives JSONL, `-o` writes the final message, sessions
**persist to disk**, and **`codex exec resume --last` resumes with full context**. The skill's old
claim that a run "is not steerable — kill it and re-delegate" was **wrong**.

**Decided (owner): keep the headless personal skill, do NOT install herdr.** The npm package
`herdr` is a **0.0.0 reserved-name placeholder**, and the plugin skill requires running Claude
Code *inside* a herdr terminal session — the owner works in the VS Code extension and is staying
there. Revisit only if herdr ships a real release.

The skill now tees the run to a log and **must give the owner the `tail -f` command as its own
line**; that replaced the herdr pane. A cold-start guardrail was added: Codex will not know
Aevia's "looks like a bug, is not" decisions, so the relevant warnings go into the task file
verbatim, or the task is not delegated.

**Also settled (owner): stay in the VS Code extension, do not move to a terminal.** Session
numbering is an Aevia convention in `sessions/`, not a Claude Code feature, and transcripts are
stored per project folder — so nothing is stranded either way.
