## 1. "Failed to fetch" loading a paid order into the staff engine — ROOT-CAUSED + FIXED (live infra)
**Symptom:** loading an existing (paid, PDF-generated) order into the staff engine threw
*"Failed to fetch"* in the order-status line.

**Root cause:** last session's EU migration (S72, ADR-0006) copied the photo *data* US→EU
but did **not** copy the bucket's **CORS configuration**. The new bucket `aevia-uploads-eu`
had *no CORS policy*; the old US bucket had `origin:["*"]`, methods GET/PUT/OPTIONS. Order
load calls `urlToFile()` → `fetch(signedUrl)` → `.blob()` (template-engine.html:4210) — a
cross-origin read that the browser blocks without CORS, surfacing as the generic TypeError
"Failed to fetch". (Would also have broken **new uploads** = PUT to the EU bucket.)

**Fix (free, no egress, reversible):** applied the identical CORS policy to the EU bucket:
```
gsutil cors set eu-cors.json gs://aevia-uploads-eu
# [{"maxAgeSeconds":3600,"method":["GET","PUT","OPTIONS"],"origin":["*"],
#   "responseHeader":["Content-Type","Content-Length","Authorization"]}]
```
Verified applied. Owner confirmed orders load again. **This is a live infra change, not a
file** — already in effect everywhere (live + local), no deploy needed.

## 3. Papercut heart page (FP1) layering — FIXED
**Wanted layering:** page bg → heart-shaped photo → balloons/clouds *on top*.
**Was:** `FP Birthday 02 Right.svg` is ONE file containing both a solid light-blue heart
backing (group `f`: `#ddecf0` rect clipped to the heart) **and** the decorations (balloon/
cloud groups h,j,l,n,p). A single `overlayAbovePhotos` flag can only put *both* behind
(earlier complaint) or *both* in front (then the solid heart covers the photo).
**Fix:** removed group `f` (the solid-heart backing) from the SVG + set FP1
`overlayAbovePhotos: true`. The photo is already independently heart-clipped (engine
`heartClip`), so the solid backing was always invisible under the photo — removing it costs
nothing visible and gives the exact layering. One SVG edit + one data flag, applies to
engine/customer/PDF with no code change. (Rejected the heavier "split into two layers"
approach — 4 code paths for zero visible gain.)
NOTE: the SP4 + Cover `overlayAbovePhotos:false` decisions are still correct + untouched —
those are the *intentional* "art behind photo" pages. FP1's `false` was a stray value.

## 4. False low-res yellow border/badge — REMOVED (engine + customer-preview)
Since chunk-023 the engine + customer-preview load the ~1600px **web derivative** (egress
optimisation), not the original. The low-res check `Math.min(w,h) < 1500` therefore
false-flagged **every** real-order photo (a 3:2 derivative's short edge ≈ 1066px). Owner
judged it adds no value → removed the yellow slot outline + "⚠ Low res" sidebar badge in
`template-engine.html` and the badge in `customer-preview.html` (parity). Left explanatory
comments + kept the `lowRes` computation (still used in debug logs).
**The genuine safeguard is intact:** order-form upload checks full-res originals + warns the
customer (S40, threshold 1575px); the PDF always renders from originals. The engine/preview
were measuring the downscaled copy — never the right basis for a print-res judgement.
