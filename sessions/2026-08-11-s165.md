# Session 165 — 2026-08-11

Customer-entered data was going missing between the order form and the two places staff read
it. Three defects, three different causes — one of them not in the code at all. Two commits:
`ff234e4`, `5e62914`, plus the seven from S163/S164 that had been sitting unpushed.

---

### 10:30 — The ask, and why the first answer was wrong

Owner reported three things about his Wander order AEV-094: the album name and spine name were
missing from the engine's "Customer's order data" panel, missing from `order-details.txt` in
GCS, and rendered **twice, overlapping** on the cover. Goal stated as: never lose a field the
customer typed.

Investigated before asking anything, which changed the shape of the work — the three symptoms
have three unrelated causes and only two are code.

### 11:00 — Two hardcoded maps, seven templates

`showOrderInfoPanel` labelled everything from maps written when only Scribble and Papercut
existed:

```js
coverLabels = { year, name, spineName, spineYear }
fpLabels    = { FP1: 'Birthday wishes', … }
```

Actual cover caption keys: Scribble/Papercut `year,name,spineName,spineYear`; **Wander
`front,spine`**; **Joyride `name,subtitle,spine,spineSub`**; **Newborn/Tender
`name,subtitle,spine`**; **Heirloom `name,spine`**. So Wander showed nothing and four
templates showed only `name`. Confirmed live: AEV-094's panel rendered exactly one row, the
itinerary, labelled **"Birthday wishes"**.

**Worth carrying: the absurd label is the only reason this was ever noticed.** The silent
losses — Tender's subtitle and spine, Heirloom's monogram — were found only by going looking.

### 11:30 — `order-details.txt` has never contained cover text. Ever.

`functions/upload.js` receives `coverCaptions`, stores it to Firestore, puts it in the staff
email, and **never writes it to the file**. Verified empirically, not inferred: dumped
`order-details.txt` for all 94 orders, filtered to the owner's four real email addresses, and
read all **38 orders across all seven templates**. Not one contains a cover or spine caption.

**Firestore always had it**, so nothing was ever destroyed — but neither surface staff
actually read showed it. Also found `fp1: [object Object]` on every Wander and Joyride order
(the itinerary survives higher up the same file under `Special requests`, so it was
duplicate-and-broken rather than the only copy).

### 13:00 — The double-render: four hypotheses, three wrong, and the owner had it right

Chased in order, each killed by evidence:
1. *Stale duplicate cover row* — `rerenderCover` uses `querySelector` (first match only), so a
   second row would be permanent. **Killed:** `renderBook` clears `#book-canvas` wholesale.
2. *Transient double-render at two spine widths* — the 3px offset is exactly Wander's
   `delta = 10mm − 9mm` at SCALE 3, which fit suspiciously well. **Killed:** installed a
   MutationObserver + wrappers on both render entry points *before* the order load; across 110
   snapshots, never more than one row, one node per key, one position.
3. *Baked text in the SVG* — **wrongly killed.** `grep "Dolomites" Cover.svg` → 0 matches, and
   `document.querySelectorAll('.cover-canvas svg text')` → `[]`.
4. *Owner's hypothesis: "layer 1 is the default text, layer 2 is mine, identical here."*
   I dismissed it after checking the CSS `:empty::before` placeholder (which renders
   `data-label`, i.e. "Front — album name") and the caption write path (one key, one write).

**He was right.** Screenshotting the caption region at 2× reproduced the doubling; rendering
`Cover.svg` **standalone** showed "Dolomites, 2026" sitting in the artwork on both the front
panel and the spine — **outlined as vector paths**, which is why grep found no characters and
why the DOM query found nothing (the SVG loads as an `<img>`). The engine was correctly drawing
the customer's caption on top of artwork that already had text there. **It reaches print** —
`export-pdf.js` embeds the same SVG.

The string collision is what hid it: `wander-data.js`'s `placeholder` was copied *from* the
artwork, so the order form suggested that exact wording and the owner typed it back. Two
identical strings read as a double-render bug. A customer typing "Tuscany, 2027" would have
seen it instantly.

**Watch out for:** all ten cover SVGs were then rendered standalone — `qa/probe-cover-svg-text.mjs`,
~20 seconds. Every other template is clean (zero `<text>` elements across all ten files, and
the four Heirloom colourways are structurally identical at 66 paths). **Wander was the only one.**

### 14:30 — The owner's re-export reverted the viewBox patch. Twice.

He replaced the SVG himself (correct — it is an asset defect). Both attempts came back with
`viewBox="0 0 5245 2788"` then `"0 0 5256 2788"` — the **full-bleed artboard**, ratio 1.88
against the required trim ratio 2.045. `tests/cover-svg-viewbox.test.js` caught both by name
("off by 8.0% — this is the FULL-BLEED artboard"). Patched to
`viewBox="212.598 212.598 4830.71 2362.2"`.

The first export was also **1mm narrow** (trim 408mm, not 409 — 409 = 200 back + 9 spine + 200
front). Flagged as a print question rather than guessed at; his second export fixed it.

**The instruction that actually prevents recurrence has nothing to do with an export
checkbox.** There is no "Use Artboards" option in Illustrator's Save As, and there does not
need to be: **Illustrator always writes the artboard as the viewBox.** So the artboard must BE
the trim (409×200mm) with the 18mm bleed set in Document Setup, artwork extending past it. The
patch lives downstream of the export, which is why every redraw discards it.

### 16:00 — Fixes, and a guard test that is the actual deliverable

1. **Panel reads the template.** Labels from each caption def's own `label` — every data file
   already had good ones. An undeclared key still renders under its raw key, so a renamed data
   file cannot make customer text disappear. Also stopped interpolating customer text into
   `innerHTML`. Verified live on four orders: AEV-094 (Wander, was 1 row → 3), AEV-070 (Tender,
   gained subtitle + spine), AEV-088 (Heirloom, gained spine + monogram + initials), AEV-072
   (Scribble, unchanged — no regression).
2. **`upload.js` writes a `Cover text:` block** and `formatFpValue()` replaces the
   stringification. **Labels ride in from the client** (`coverCaptionLabels`, new field)
   because `functions/` has no access to the template data files — checked.
3. **`tests/order-data-completeness.test.js`**, 31 tests. Asserts the **shape** that makes the
   bug impossible (no hardcoded label map; labels come from the template; undeclared keys still
   render; `formatFpValue` never emits `[object Object]`) rather than today's key names — the
   original map passed every eyeball because it was correct for the templates that existed when
   it was written. **All four structural assertions verified to FAIL against HEAD.**

441 tests green (was 410). `qa:order` 12/12. Panel fix confirmed on the live rig after deploy.
