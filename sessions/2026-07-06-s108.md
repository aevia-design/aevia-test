## 2. Reposition ✥ button on special-page photos (`182187d` staff, `3f09354` customer)
Owner: the "Our story" page had working reposition but no ✥ button, unlike normal
photos. Root cause: special slots (pool ≠ regular/cover — story/words/toy/steps/
artwork) used invisible **always-on drag** with no handle. Fix: extracted a shared
`attachRepositionHandle()` helper in each engine and gave special slots the same ✥
button as regular slots (they're not swap-draggable, so the button just toggles
reposition mode).
- **Staff engine**: all special slots now show the button.
- **Customer preview**: special slots show the button AND keep their swap/remove lock
  (not-allowed cursor + lock toast). The edit-hint already promised "Click ✥ on a
  photo to move it inside its frame", so this makes the UI match the copy.
- **Heart + cover slots deliberately NOT given the button** — they're clip-masked
  (heart shape / Tender ellipse), so a corner button gets clipped away. They keep
  always-on drag (owner chose this "option 1"; option 2 = an out-of-clip handle, was
  declined for now). So the ✥ instruction is slightly inaccurate for heart/cover only.

## 3. Engine-disparity investigation + tripwire (`0ce724e`)
Owner worried he must "check 2 engines every time." Reviewed how they're wired:
- **SHARED (single source of truth, change once):** all 5 `*-data.js` files (every
  geometry/caption/colour), plus `photo-utils.js`, `book-completeness.js`,
  `map-render.js`.
- **DUPLICATED (parallel inline copies, change twice):** the render pipeline — ~29
  functions with identical names inlined in BOTH `template-engine.html` (4669 lines)
  and `customer-preview.html` (2949 lines): renderCover, renderSpread, attachCropDrag,
  getHeartCrop, buildBookSequence, resolveVariant, applyTypographicRules, etc.
- **Evidence of real drift:** `assignPhotosToSpreads` / `resolveVariant` bodies already
  differ (staff has FP drag-drop "pinning" via `_fpAssignments`; customer is simpler).
  Some drift is intentional (customer read-only/payment), some is just formatting.
- **Key insight explaining the session's two "bugs":** they were NOT engine divergence.
  Caption geometry is SHARED data → nothing to mirror → the customer showing the old
  222.5 could only be a stale cached `tender-data.js`. And the button needed a
  per-engine edit (made in both), but the customer file was cached. **Owner had been
  testing the LIVE site while the 3 commits were still local/unpushed.** Pushing +
  hard-refresh fixed both. Confirmed working.
- **Guardrail shipped:** `tests/engine-parity.test.js` — checks all 29 shared render
  functions exist in BOTH engines; fails (naming the missing fn + engine) if one side
  drops one. Presence-only, not function bodies. Verified it trips (added a fake name →
  red) and passes now. `npm test` = 167/167.
