## 1. Native mobile app — deferred, not rejected

Owner opened a `/shaping` session on building an iOS app (order → light edits → approve/pay → track status), motivated by a real inconsistency: **customers are told to upload from their phone (for EXIF dates) but can only edit the preview on a laptop.** Secondary motive was loyalty, given the planned yearbook/calendar/occasion roadmap.

Landed on **defer until after the F&F trial and first real orders**. Full reasoning in `docs/briefs/ios-app.md`; TO-DOS #40 repointed at it (its old "Capacitor wrap, no rewrite needed" framing is superseded).

**What actually decided it:**
- **Owner time is the binding constraint.** Cash cost is ~€0 ($99/yr Apple, ~$30/mo MacInCloud). The real price is 2–3 months part-time, which collides with print house (Aug) → F&F (Sep) → marketing (year-end).
- **It optimises the wrong end of the funnel.** An app is retention infrastructure; there are zero customers to retain.
- **The strongest technical argument collapsed.** Background upload surviving a locked screen is the one thing only native provides — but realistic orders are **~150–200 MB (40p, ~55 photos)** and **~300–450 MB (80p, ~110 photos)**, and the owner's existing iPhone tests already cover that range. ⚠ The **1–4 GB/order figure in `CLAUDE.md` is wrong** and was the source of the inflated case. Needs correcting; the right number is unknown to Claude.
- Owner named the "pet idea" element himself, which is recorded in the brief so future-us weighs it correctly.

**Architecture direction if built:** native shell (order/upload/pay/status) + editing engine in a WKWebView. Not a Capacitor wrap, not a native engine rebuild — the engine is print-critical geometry, and two implementations that must agree exactly is how a customer approves a preview that doesn't match what prints. Also worth knowing: **JS logic ports to React Native/Flutter; DOM/SVG rendering does not.**

**Engine extraction: raised, then killed.** Measurement found **29 of 52 customer-engine functions share names with the staff engine**, including the whole render path. It was proposed as a prerequisite to the app. **That claim was false** — a webview can point at `customer-preview.html` as-is. Parked; see LEARNINGS 2026-07-22.

## 2. Mobile fixes — shipped and verified (`2bd4a84`)

All four were **CSS-only in shared files**. No copy, no markup, no per-page edits. Owner's constraint: copy must not diverge between mobile and desktop (desktop is verified, and DE mirrors double any divergence).

| Issue | Fix | File |
|---|---|---|
| Value cards cramped, headings misaligned | `.touch-grid` → 1-up on mobile | `mobile.css` |
| Orphan words ("We do the rest.") | `text-wrap: pretty` on body copy | `type.css` |
| Footer endless, half the width unused | Link groups 2-up, brand spans both | `mobile.css` |
| DE interrupting the burger menu | `order:` on `.nav-account` / `.nav-lang` | `mobile.css` |

**Cards:** at 2-up a card was ~165px wide → 2–3 words per line. 1-up gives ~350px → 7–8 words. Going 1-up also made the desktop `.touch-name { min-height: 3.2em }` equalisation unnecessary on mobile — cards alone on a row cannot misalign.

**Widows:** `balance` evens line *lengths* (correct for headings, left alone); `pretty` prevents a lone last word (correct for body). Declared in `type.css` because it loads after each page's inline `<style>`, so it overrides the `balance` those desc classes carried — same specificity, later source order. Safari 17.5+; Firefox ignores it harmlessly.

**Nav:** reordered with flex `order` inside the mobile media query rather than in markup — **1 file instead of 29.**

**Verified** with Playwright at 390 / 375 / 1440px: 10/10 assertions, no console errors, **desktop unchanged** (cards still 4-up, footer 4-up, `min-height` 57.6px intact). Owner confirmed the result on his phone.

## 3. Google sign-in on iPhone — diagnosed, briefed, deferred (`4b431ea`)

Full brief: `docs/briefs/google-signin-ios.md`. TO-DOS **#86**, High, gated on the F&F trial.

- **Two call sites, not one:** `account.html:406` and **`order.html:2817`** — the second is inside the purchase path and had not been noticed.
- **The naive fix does not work.** `authDomain` is `aevia-uploads.firebaseapp.com`, a different domain from the app, so `signInWithRedirect` is also blocked on Safari 16.1+ / Chrome 115+ (cross-origin iframe → third-party storage).
- **`signInWithPopup` is not wrong** — it is Firebase's own Option 2 and is recommended for non-Firebase hosting. Its documented weakness is mobile popups.
- **Structural snag for the proper fix:** Firebase Option 3 (reverse-proxy `/__/auth/`) needs a Cloudflare Pages Function, but Cloudflare auto-detects a root `functions/` dir — and **this repo's root `functions/` is Firebase Cloud Functions.** They collide. `_redirects` cannot substitute (Firebase requires transparent proxying, not 302s).
- **Device evidence (owner):** the tab **does** open on iOS Safari, **but not every time.** Intermittency is the signature of the *user-gesture timing* problem — `signInWithPopup` does async work before `window.open`, and on a cold load the gesture token expires. This makes a cheap pre-warm fix (Option A) more plausible than first judged.
- **Still unanswered:** when the tab *does* open, does sign-in complete, or does it still strand the user? That decides cheap-fix vs the proxy work.
- Four options, **all €0**. S146 recommendation: hide the Google button on mobile now, do the proxy properly later — recorded as input, not a decision.
