### Tender was re-authored at 410mm — `referenceSpineMm` 9 → 10
**Decided:** Tender's sheet went 409 → 410mm (`viewBox` 1159.37 → 1162.205) and its ellipse
now sits at exactly 315.0mm. It is authored in 10mm-spine space like Heirloom and Laguna, so
it must declare `referenceSpineMm: 10` — with `9` the engine sizes the SVG to 409mm and
squeezes a 410mm sheet into it (the Wander stretch mechanism, smaller).
Its spine caption moves 222.5 → 223 to keep the offset-from-spine-centre at zero; both values
resolve to 205mm, so the change is neutral, but the two must move together.
**Watch out for:** `sections.spine.wMm` and `sections.front.xMm` are read **nowhere** in the
geometry — only `spine.bgColor`, `back.wMm`, `front.wMm` and the panel colours are. They were
updated to match reality but they do nothing.

### AEV-096 explained — and the upload stall is still NOT solved
**Answered:** the bucket held 28 of 56 photos because photo 29 failed, the circuit breaker
tripped, and **photos 30–56 were never attempted.** AEV-096 *is* the order that prompted the
fix — `order.html:2929` names it and `fc1145a` landed the same day it was placed, so its record
predates the fix. **The cascade is fixed** (`bb311f1`, `fc1145a`): today it would lose one
photo, not 28, and retries now back off 2s/5s rather than 100/200ms.
**Not answered — the stall itself.** `upload-failures.md` has been CLOSED-unproven since S150
waiting for a capture. This is the capture, and it **killed the duplicate-`File` hypothesis**
(55 pool photos, 55 distinct originals, the failing file used exactly once; Chrome on Windows,
not Safari). But it did not establish a replacement.
⚠ **A correction that matters.** All three attempts stopped at exactly 371,712 bytes, and this
session first read that as proof the file could not be read. **That reading is not sound.**
`bytesTransferred` is only updated inside the `xhr.upload.progress` handler and **we never
record how many progress events fired**, so "one event at a 363 KiB buffer flush, then the
connection wedged" fits the same data. The evidence cannot separate a file fault from a
transport fault.
⚠ **The OneDrive explanation weakened.** The owner confirmed the photos lived in a OneDrive
folder, but **"Free up space" is greyed out on them** — so they are not placeholders and there
is nothing to hydrate. A third candidate survives regardless: OneDrive rewrites files during
sync, and Chrome's `File` is a snapshot tied to modification time, so a file touched mid-upload
fails to read whatever Files On-Demand is set to.
**Decided (owner): nothing to build.** `work/upload-file-read/brief.md` was written and is
**PROVISIONAL** — its premise is unproven and its prevention scope is not justified. What stays
defensible is instrumentation (record progress-event count and timestamps; distinguish an
unreadable file from a stalled transport), not a fix.
**Ruled out of that brief deliberately:** resumable uploads (owner). The signed URL uses
`action: 'write'`, documented as a single-shot PUT that is **not** resumable, so every retry
restarts at byte zero. Worth doing for weak networks, its own session — and it would **not**
have fixed AEV-096.
**Two smaller defects found, not fixed:** the engine throws away the HTTP status
(`template-engine.html:5077`) so "gone forever" and "link expired" read identically; and
`getOrder` checks `.exists()` before signing derivative URLs but **not** originals
(`functions/index.js:223`), so a missing original yields a dead signed URL instead of a null.
