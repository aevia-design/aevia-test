## 1. Upload failure — investigated, instrumented, NOT solved

Systematic debugging on three mock orders that stranded at `status: uploading`. **The starting assumption was wrong and the evidence overturned it.**

**"It stalls on the last photo" is a display artefact.** The uploader runs 5 workers in parallel and the counter increments on completion in any order, so *one* file hanging anywhere renders as "N−1 of N". It looks like the last photo regardless of which file it actually is.

**What actually failed** (GCS cross-checked against the Firestore manifest):

| Order | Template | Expected | Missing |
|---|---|---|---|
| AEV-067 | Wander | 55 | photos 049–055 (trailing block) |
| AEV-073 | Papercut | 50 | `special_pages/fp4.png` |
| AEV-074 | Papercut | 50 | `special_pages/fp4.png` |
| AEV-075 | Papercut | 50 | `special_pages/fp4.png` |
| AEV-072 | Scribble | 50 | none — succeeded, *including its own fp4* |
| AEV-076 | Papercut | 50 | none — succeeded, fp4 selected |

**Papercut/fp4 is 3 failures, 1 success.** ⚠ It was called "deterministic" mid-session on 3-for-3; AEV-076 disproved that. Too concentrated on one slot to be chance, but not deterministic. AEV-067's trailing block is a different shape — one worker throwing rejects `Promise.all` and abandons the queue.

**Ruled out:** index desync between `fileObjects` and `filesMeta` (built in lockstep, `order.html:2274-2312`); a skipped file selection (a skipped slot never reaches the manifest, and fp4 *is* in the manifest, so a real file was sent and its PUT failed).

**Two real defects found regardless of root cause:**
1. **The retry is decorative** — 3 attempts at 100/200ms backoff all land inside half a second. Deliberately left alone: if a retry fails identically, that is evidence the failure is deterministic rather than transient.
2. **One dead file kills the whole batch** — the worker rethrows, `Promise.all` rejects, queued files are abandoned. That is the AEV-067 signature.

**Instrumentation shipped** (diagnostics only, no behaviour fix): per-attempt HTTP status, GCS error body, exception and **timings**; a `reportUploadFailure` function storing them as `uploadErrors` without touching status or email; `scripts/inspect-upload-failure.js` to read it back and cross-check the bucket.

**Then a second gap appeared.** The owner reported the tab was never closed and the upload simply never finished. **A stalled fetch never rejects, so the catch that reports failures never runs** — the instrumentation as first shipped could not have caught this. Added a 60s `AbortController` timeout per attempt so a stall becomes a recorded failure; `AbortError` is logged as `TIMEOUT` so "stalled" stays distinguishable from "refused".

**Unproven hypothesis, recorded for the next occurrence:** Xenia's test set reuses one source photo across cover/special/pool (identical byte sizes in AEV-074), and slots 1–5 upload concurrently. Safari streaming the same `File` into two simultaneous requests would explain both the concentration on an early special slot and the browser-specificity. **The decisive observation is whether the photo assigned to fp4 is also used elsewhere in the same order.**

Full evidence log + reporting procedure: **`docs/briefs/upload-failures.md`**.

## 2. Pre-launch banner (`6b66bb1`)

Three owner asks, all in `assets/js/site-mode.js`.

- **Overlap.** Not a thickness problem: `.nav` is `position:fixed;top:0` (`product.css:10`) while the banner is injected into normal flow at the top of `<body>`, so the nav rendered *underneath* and lost its top strip — that is what was slicing the logo. Fixed by offsetting `.nav` by the banner's measured height, re-measured on resize because the text wraps to two lines on narrow phones. **Page content needed no change** — the banner is in flow, so everything below already shifts by the same amount and the existing offsets still line up. Also slimmed 32px → 28px.
- **Copy**, locale-aware off the `/de/` path segment. EN: "Our site is still being built. Aevia opens autumn 2026. Join the waitlist →". DE: "Unsere Website ist noch im Aufbau. Aevia eröffnet im Herbst 2026. Zur Warteliste →".
- **Colour** `#1a1a1a` → `#9a3b26`, a deep terracotta. A saturated red reads as *discount sale*, wrong for a craft brand; terracotta is as prominent against the off-white but stays in the warm editorial family and sits with `--accent-dk` (#a8895f).

**Verified** with a new `qa/prelaunch-banner.mjs`: 16/16, EN + DE at 1440 and 390px, nav and logo clear the banner at both, no console errors.

⚠ Owner asked for "autumn 2026"; **S130 had deliberately avoided a hard date** (a stranger can screenshot a promise). Accepted because a season + year is not a date you can be held to. Flagged, not silently overwritten.
