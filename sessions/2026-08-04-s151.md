## 1. Cloud photo import — scoped, then dropped

Owner proposed letting customers import photos from iCloud and Google Drive rather than only
from local disk. Investigated and **dropped before any code was written.** Three findings:

- **iCloud is not buildable at any price.** No public API lets a website browse a customer's
  iCloud Photos; CloudKit JS only reaches a container the app itself owns. This is Apple's
  deliberate position, not a gap in our implementation.
- **Phone pickers already cover it.** The iOS picker reaches iCloud Photos/Drive natively, and
  the Android picker surfaces Google Photos and Drive the same way. On the devices where
  customers most plausibly keep photos, cloud import already works through the OS with zero
  integration on our side. The feature would have served desktop users only.
- **Fidelity was the real risk, not the OAuth paperwork.** Photos fetched through Google's API
  can come back with EXIF stripped or altered and not necessarily at original quality. We read
  EXIF with exifr, and this is a printed product — "not byte-identical" matters. Had we built
  it, the first thing to build would have been a throwaway byte-comparison test, not the feature.

An earlier claim in-session that Google verification would take weeks was **overstated**: that
applies to broad-access scopes, and the picker-only route (we receive only the files the
customer explicitly selects) avoids the heavy review. Corrected in the same conversation.

## 2. The 60-second upload timeout — the actual launch risk

Ran through the upload path looking for what breaks at F&F. The strongest candidate is not #88
but the per-attempt timeout at `pages/order.html`, which the S147 comment itself flags as a
**diagnostic** threshold set on a studio connection and explicitly marks "revisit before real
customers upload over slow mobile links."

It has never been revisited. A 12 MB photo on a weak 1 Mbit uplink legitimately takes ~95
seconds; on poor signal, ~3 minutes. All three attempts would abort and the order would strand —
a healthy upload killed by a threshold, and indistinguishable in the logs from the real fault
chased for three sessions.

**Raising the number is not the fix.** At five minutes a genuinely dead upload hangs for
fifteen. The defect is that the timer measures *elapsed time* rather than *whether bytes are
moving*, so it cannot tell "slow" from "stalled" — the two cases needing opposite responses.

## 3. What was built (uncommitted, unverified)

Brief at `work/stall-detection/brief.md`. Changes confined to `pages/order.html` (+93/−36):

- **Stall detection.** GCS PUT moved from `fetch()` to `XMLHttpRequest` — `fetch` cannot report
  upload progress, which is the sole reason for the swap. `xhr.upload.onprogress` resets a
  `STALL_TIMEOUT_MS = 30000` timer; abort only on 30s of *no movement*. `MAX_ATTEMPT_MS =
  900000` as a backstop.
- **Byte-level progress.** Both the counter and the bar now driven by bytes including in-flight,
  so progress moves *within* a file. This also removes the "49 of 50, looks stuck" display
  artefact described in `docs/briefs/upload-failures.md`.
- **Retry backoff 100/200 ms → 2s/5s.** The old values put all three attempts inside half a
  second. They were left broken *deliberately* as evidence-gathering for #88; that reason
  expired when #88 closed in S150.
- **Failure record extended** with `bytesTransferred` / `totalBytes`, and a stall now labelled
  distinctly from a ceiling breach. `scripts/inspect-upload-failure.js` unmodified and still
  compatible.

**Out of scope, still open:** `Promise.all` at `order.html:2553` means one dead file abandons
the remaining queue (the AEV-067 signature). Correctly flagged rather than fixed.

## 4. Three defects caught by review, not by the agent

The delegated developer-agent's first submission had three real defects, all found by reading
the diff:

1. **It reintroduced the bug it was built to remove.** `xhr.upload` progress events stop once
   the request *body* is sent — but the final event had just armed a fresh 30s timer, and we
   then wait for GCS to acknowledge the object. On a large file that ack can exceed 30s, so a
   *completed* upload would be aborted and logged as a stall.
2. **The 15-minute ceiling lied about itself.** `xhr.abort()` synchronously fires the `abort`
   listener, so its `AbortError` rejection won the race and a ceiling breach was recorded as
   "no progress for 30000 ms".
3. **The progress bar was never changed** — only the byte text. `overlayFill` was still
   `uploadedCount / total`, so on a single large file the bar sits at 0% throughout.

All three were fixed on the second pass and **verified by reading the file**, not by trusting
the report. Fix 1 is sound (`if (e.loaded < e.total)` guards the rearm); fix 2 sets its flag
before `abort()`, so the label is now correct.
