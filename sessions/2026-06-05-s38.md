# Session 38 — 2026-06-05

### — Wander PDF: oversized SVG overlays missing from PDF
**Done:** Added `shrinkOversizedSvg()` helper in `scripts/export-pdf.js`. Wired into both spread and cover SVG render paths before `expandSvgViewBox`.
**Why:** Four Wander overlay SVGs (SP 04 V/H Right, SP 10 V/H Right) embed 7–17 MB of base64-encoded raster images. This exceeds libxml2's ~10 MB per-node XML limit, so `sharp`/librsvg silently drops the entire overlay. Browsers have no such limit — staff/customer engines rendered fine. Error message is "Input buffer has corrupt header: glib: XML parse error: Resource limit exceeded, try XML_PARSE_HUGE".
**Decided:** Downsample embedded rasters to ~2× their on-page display size rather than re-exporting assets. Gated at >8 MB so Scribble (largest SVG = 5.5 MB) is never touched.
**Watch out for:** Any new template SVG >8 MB will hit this same failure. The fix handles it automatically, but if a future SVG has group-level transforms (parent `<g transform="...">` wrapping the `<image>` elements) the display-size calculation would be wrong and images could be over-shrunk. Verify with `grep -o '<g [^>]*transform[^>]*>' file.svg` before assuming the fix applies cleanly.

### — Wander PDF: caption line-wrap discrepancy
**Done:** Fixed `stripHtml()` in `scripts/export-pdf.js` — added per-line whitespace collapse and trim at the return value.
**Why:** contenteditable on Windows stores manual line breaks as `\r\n` + `<div>`. After HTML stripping, `\r` remained as a trailing character on the first line. pdf-lib rendered `\r` as a glyph advance, inflating the measured line width just enough to push a word to the next line — the browser ignored the `\r` so the engine showed one line, the PDF showed two.
**Watch out for:** The same `\r` issue will occur in any caption edited on Windows. The fix (`split('\n').map(l => l.replace(/[ \t]+/g, ' ').trim()).join('\n')`) handles it universally at the stripHtml level, so all templates and all future fonts benefit automatically.

### — Wander PDF: fontkit GSUB ligature bug — Cormorant Garamond
**Done:** Added `'Cormorant Garamond'` to `LIGATURE_FONTS` in `scripts/export-pdf.js`. Split the "suppress letter-spacing" concern into a separate `SUPPRESS_LETTER_SPACING_FONTS` set (EB Garamond only). Cormorant Garamond now uses char-by-char drawing (`drawTextNoLig`) but keeps its defined `-0.02em` letter spacing.
**Why:** Same `@pdf-lib/fontkit` GSUB bug as EB Garamond (documented in session 2026-05-27): fontkit applies ligature substitution when `drawText` receives a full string — the ligature glyph's advance width is stored incorrectly, causing a visible gap after the substituted glyph. Per-character drawing avoids the bug because there is no shaping context across individual calls. The gap appeared between "if" and "Wander" in Wander captions.
**Watch out for:** **Every new font added to the project must be checked for this bug.** Symptoms: engine renders the caption correctly, PDF shows an unexpected gap at a specific character position (typically after 'fi', 'fl', 'ff', or other ligature pairs). Diagnosis: add the font to `LIGATURE_FONTS`; if the gap disappears it's the fontkit bug. If the font requires letter-spacing, do NOT add it to `SUPPRESS_LETTER_SPACING_FONTS` — only EB Garamond suppresses spacing. The `drawTextNoLig` path correctly applies `characterSpacing` per character.

### — Wander PDF: stripHtml false-positive warning
**Done:** Fixed the naive comparison in `stripHtml` — the naive path now mirrors the same `<br>`/`<div>` → `\n` conversion as the stripped path, so captions with manual line breaks no longer trigger a spurious "unhandled HTML tags" warning.
**Why:** The old naive path removed all tags without converting to newlines first. Any caption with a `<br>` or `<div>` produced a stripped ≠ naive mismatch and fired the warning, even though those tags were handled correctly. This was pure noise masking real warnings.
