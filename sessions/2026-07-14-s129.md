### Joyride-specific (stage 4)
- **Cover renders all 4 photo slots.** `renderCover` read `coverDef.slots[0]`; now loops
  `coverDef.slots`, taking photo *i* from `window.specialPhotos.cover[i]`. Per-slot placeholder
  label derived from the slot key (`coverTop` → "Cover photo — Top"). Wander's `slots: []`
  no-ops. Crop/reposition already keyed off photo NAME, so the loop body was unchanged.
- **Cover captions auto-shrink.** `capDef.autoShrink` steps the font down 1pt at a time (floor
  50%) until content fits `hMm`. Two flaws caught while extending it to the spine: it did not
  rescale `line-height` (baked as fixed px from the base size, so the leading stayed loose and
  the box still overflowed), and **rotated** captions are vertically centred using one line's
  height, which moves when the size changes. Both fixed. Applied to all four cover captions.
- **De-hardcoded spread lists.** `standardTypes` + `fpTypes` (type dropdown) and `stdIds`
  (sequence builder) were hardcoded `SP1–SP6`; now derived from the active template's own keys
  (`/^SP[1-9]\d*$/`, numeric sort). SP7–SP9 reachable; bogus FP options gone. Mirrored into
  `customer-preview.html`'s `buildBookSequence`.
- **M-page allocation** (SP4/SP8 right). The multi-slot branch of `assignPhotosToSpreads` picks
  a same-orientation PAIR, which cannot serve a page that fixes one vertical + one horizontal
  frame. For a `mixed:true` variant each slot now matches its own `orient` against the spread's
  photo window independently, falling back to crop-into-frame + a `console.warn`. Verified: SP4
  right gets V then H.
- **Slot `zIndex`** — vertical photo renders on top where the M-page frames overlap.
- **`textPanelTitle`** — new render block before `textPanel`, same toolbar/save path, keyed
  `'textPanelTitle'`. Intro shows both text boxes. (Customer + PDF mirror at Phase B.)

### Pre-existing bugs found + root-caused (hit EVERY template, not just Joyride)
1. **`window.bookCaptions` was never initialised** in the GLOBAL STATE block — every sibling
   global is. It was created lazily inside `renderBook`, but `renderCover` reads it
   **unguarded**, so **uploading a cover photo before any pool photos crashed the engine**
   (`Cannot read properties of undefined (reading 'cover')`). **Reproduced on Tender.** Fixed by
   initialising it with the other globals.
2. **FP text panels never applied their CSV `captions_color`** — the `textPanel` block set
   font/size/weight/spacing but not colour, so panels inherited the `.slot-caption` CSS default
   and every template's `captions_color` was silently ignored (Joyride's red route text, and
   Wander's navy, both). Cover captions already read `capDef.color`; text panels now do too.
   *Found by eyeballing the map spread — a smoke test cannot see a wrong colour.*
3. **Local-mode cover upload was capped at 1 photo** (`data-max="1"` hardcoded in markup). Now
   driven by the template's own `cover.slots.length`; input goes `multiple`; label follows.

## The 28mm spine — RESOLVED (it was an artboard error)

S128 flagged Joyride's spine as 28mm (vs 9mm everywhere else) and asked Xenia. Owner queried it
this session; I re-verified against the source and the reading was correct (SVG header said
`width="428mm"`, and the CSV's spine-caption centre corroborated). **Xenia confirmed the export
was wrong** and re-issued both the cover SVG and the cover CSV mid-session.

Cover is now the standard **409mm (200 + 9 + 200)**. Two independent checks agree: SVG is
`408.774 × 200mm`, and the spine-caption centre sits at x=204.5 without bleed = 200 + 9/2. The
photo grid now centres on x=309 = the front page's TRUE centre — **the old "grid sits 5mm
off-centre" anomaly was the same error.** Slots resized 60→57mm, title 35→33pt in a 50×41 box.

**This had been masking a real bug:** the engine's `.cover-canvas` is hardcoded
`width: 1227px !important` (= 409mm × 3px/mm), so the 428mm cover was being **chopped 19mm short
and the right-hand cover photo was clipped off the canvas.** With the corrected artboard the
hardcode is right and nothing needs changing — but it is a latent trap for any future template
whose cover is not 409mm.

## Cover caption sizing — measured, not guessed

Owner asked how to size the spine sub-label box. Measured in the real fonts at 12pt rather than
guessing: `July, 2026` = **19.3mm** in a **20mm** box (fits by 0.7mm → wraps on rounding);
`December, 2026` = 32.3mm; **`September, 2026` = 34mm** (the longest realistic date). Recommended
**35mm**; owner applied it, and capped lengths at **30 (spine) / 20 (spine sub)**.

Those caps sit slightly ABOVE what the boxes physically hold at full size (measured: 27 chars
spine, 16 chars sub). Rather than overrule his numbers, **autoShrink was added to all four cover
captions** — so a 29-char spine label steps 12pt → 9pt and still fits one line. Verified: every
cover caption stays inside its box at its maxLength.
