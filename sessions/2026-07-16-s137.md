**What changed:** only the `Frame` group, only vertically — every y dropped by exactly 1.133 SVG

**Whether the data had to follow it — measured, not guessed.** Converting the frame windows to mm
(`200 ÷ 566.929 = 0.352778` mm/unit) and comparing to `joyride-data.js:255-256`:

| slot | frame window (new SVG) | data file | gap |
|---|---|---|---|
| 1 (vertical) | centre 60.22, 66.84 · 80.000×107.000mm | x 60, y 67 · 80×107 | 0.22 / 0.16mm |
| 2 (horizontal) | centre 136.08, 146.18 · 107.000×80.000mm | x 136, y 146 · 107×80 | 0.08 / 0.18mm |

Widths/heights match to three decimals on both slots, which is what confirms the right windows are
being read. Every gap is **≤0.22mm** — below the 1mm granularity the CSV even records.

**The old SVG was the misaligned one:** slot 2's frame centre was at 146.58mm against data 146 —
out by **0.58mm**. The new export lands at 146.18. So Xenia moved the frames **to match the coords
the owner rounded in S136**, not the other way round. The re-export *improved* alignment; syncing
the data to it would have been backwards.

`sync-joyride-csv.mjs --dry-run` independently agrees: "already in sync". CSV untouched.

**Method worth keeping:** SVG frame → mm → centre, compared against the JS. `x`/`y` in the data are
the **content-origin centre** (not top-left, not bleed-origin) — proven here by w/h matching exactly
and x matching to 0.08–0.22mm on both slots. That's four independent agreements; a mapping this
cheap to validate should always be validated before touching data.

## 3 — The S136 gcloud recipe was wrong twice (`bash: gcloud: command not found`)

STATUS.md:29 told this session to run
`export CLOUDSDK_PYTHON=$(ls -d /usr/lib/google-cloud-sdk/platform/bundledpython*/bin/python3 | head -1)`.

- **`/usr/lib/google-cloud-sdk` does not exist on this box.** The SDK is at `~/google-cloud-sdk`.
- **It fails silently.** The `$(ls -d …)` substitution finds nothing → `CLOUDSDK_PYTHON` is set to
  the **empty string**, so even with PATH fixed you'd hit a confusing Python error rather than
  "no such directory".
- **Nothing needed installing.** gcloud was already there and already authenticated — SDK 576.0.0,
  bundled python 3.14.6, account `evg.myasin@gmail.com`, project `aevia-uploads`. It was simply
  **not on PATH** (no rc file adds it). The memory `reference_codespace_tooling` said "same
  disposability applies to gcloud", which pointed the wrong way.

Correct form, from the repo root:
```bash
export CLOUDSDK_PYTHON=/home/codespace/google-cloud-sdk/platform/bundledpythonunix/bin/python3
export PATH=$PATH:/home/codespace/google-cloud-sdk/bin
gcloud run deploy aevia-pdf-renderer --source . --region europe-west1
```
Per-shell; a new terminal needs them again. Still no `--allow-unauthenticated` (S133), still
`europe-west1` (co-located with `gs://aevia-uploads-eu`). Both memories corrected + the Windows
one explicitly scoped to Windows.
