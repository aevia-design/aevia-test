# Session 115 — 2026-07-07

## Referral program (promo codes Phase 2) — BUILT + independently reviewed, NOT committed

Built the full Phase 2 referral system from `docs/briefs/promo-codes.md` (specced S113, decided S114 to build WITHOUT dashboard payment detail). Owner switched the session to the Fable model at the start.

### What was built
- **`functions/referral-utils.js` (NEW)** — pure, Jest-testable logic:
  - `generateReferralCode(name, rand)` → `ANNA-7K2P` style (first name, max 6 letters, fallback `AEVIA`; 4-char suffix from a 31-char alphabet with no I/L/O/0/1).
  - `extractPromotionCodeId(session)` — reads the promo code used from a Stripe session (`total_details.breakdown.discounts` expanded shape + fallback).
  - `referrerRewardDecision({paymentStatus, order, referral})` — issue only when paid + known code + not already rewarded + not self-referral.
- **`tests/referral.test.js` (NEW)** — 16 tests, TDD (red first). Suite now **183/183** (was 167).
- **`functions/index.js`**:
  - **`getMyReferralCode` (NEW Cloud Fn)** — verified-ID-token gate (same as getMyOrders). First call mints the customer's unique multi-use share code in Stripe (`restrictions.first_time_transaction: true`, backed by env `STRIPE_REFERRAL_COUPON_ID`), writes `referralCodes/{promotionCodeId}` reverse index + mirrors `referralCode` onto `customers/{email}`. Commit is a Firestore **transaction**; on a double-click race the loser Stripe code is deactivated (reviewer fix).
  - **`handleReferralReward` helper**, called from `stripeWebhook` after the paid flip, wrapped in try/catch so referral failure can NEVER break payment. Re-fetches the session with `expand: ['total_details.breakdown']`, looks up `referralCodes/{promoId}`, then mints the referrer a **single-use** €10 code (`THANKS-XXXX`, `max_redemptions: 1`, `expires_at` +12 months), stamps the order `referredBy` + `referrerRewardIssued: true` and appends to `customers/{referrerEmail}.rewardCodes` in ONE batch (reviewer fix: atomic), then emails the referrer the code.
- **`pages/account.html`** — new "Refer a friend" rail tab + panel: share code + Copy button, earned reward codes listed, loads via `getMyReferralCode` in `route()`. CSS `.referral-code` (page uses `--border`, NOT `--line`). Copy stop-slopped.

### Decisions
- Share code = multi-use, referee-first-order-only; reward codes = single-use, **12-month expiry** (owner asked about limits; coupon-level date/redemption caps deliberately left EMPTY — they'd apply globally across the whole programme).
- Referrer gets an email when a reward is minted (they'd never know otherwise).
- Coupon is owner-created in the Stripe dashboard (like Phase 1), id in `functions/.env` as `STRIPE_REFERRAL_COUPON_ID` — owner added it and started the deploy this session.

### Independent review (`/reviewer-agent`) — verdict REVISE, fixes applied
1. **Fixed:** race in `getMyReferralCode` (two concurrent first calls → two codes) — now transactional + orphan-code deactivation.
2. **Fixed:** reward writes (order flag + customer reward) not atomic — now one batch.
3. **Noted in code:** 4-char suffix is enumerable at scale; lengthen to 6+ before public scale-up (comment in `referral-utils.js`).
4. **KEY OPEN FINDING — first_time_transaction may not bind for guests:** our checkout creates no Stripe Customer, so Stripe may not recognise a repeat referee → the same friend could get €10 off a second order too. Bounded damage (€10, self-referral blocked, rewards single-use). **Owner to sandbox-test redeeming the same share code twice with the same email.** If Stripe doesn't block it and it matters → option (b): look up/attach a Stripe Customer by order email in `createCheckoutSession` (touches ALL checkouts — needs owner OK, not built).
