## Session 2026-05-27 — Phase 13 visual QA + PDF font/coordinate fixes

### — Engine: funny words text panel grows from centre — DONE
**Done:** FP2 panel previously used fixed-height + padding-top valign, which clipped extra
lines downward. Replaced with `top = panelCenterY` + `transform: translateY(-50%)` + no
fixed height + `maxHeight` cap + `overflow: hidden`. As more words are added the box
grows equally up and down from the centre while staying within the designed area.
**Watch out for:** Only applies when `isFunnyWords` is true. Regular text panels (FP1
birthday wishes etc.) keep the fixed-height + padding-top approach.

### — Engine: valign:bottom slot caption + text panel grows upward — DONE
**Done:** For FP4 V left caption (`valign: bottom`), the old approach used
`paddingTop: capHeight * 0.75` which only worked for a single line — extra lines pushed
downward off the page. Replaced with CSS `bottom` anchoring (`bottom = CANVAS_PX -
capBottomEdge`), no fixed height, `maxHeight` cap. First line sits at the bottom of the
designed box, additional lines grow upward.
**Watch out for:** The AI button positioning for bottom-anchored captions uses
`(cap.yMm - BLEED_MM) * SCALE - capHeight / 2 - 24` (above the box's top edge). Same
formula as `capTop - 24` but computed inline because `capTop` is now only assigned in
the else branch.

### — PDF: slot xBleed/yBleed are CENTRE coords, not top-left — DONE
**Done:** `slotLeft`/`slotTop` in `export-pdf.js` treated `xBleed`/`yBleed` as top-left
corner. They are CENTRE coordinates (same convention as captions). Fix: subtract `w/2`
and `h/2`. This was the cause of all photos being placed massively off the page in PDF
output (slot at x=108mm with w=150mm was being placed at top-left=108 instead of 33mm).
**Watch out for:** Every coordinate in `scribble-data.js` for spread photo slots and
cover slots/captions is CENTRE-based. The only exceptions are `slot.x`/`slot.y` (no-bleed
content-area coords for engine rendering) — also centre-based.

### — PDF: cover bleed double-counting — DONE
**Done:** Cover photo slot and cover captions had `COVER_BLEED_PX/PT` added on top of
`xMm/yMm` coordinates that already include the 18mm bleed. Removed the addition in three
places: `renderCoverImage` photo `sx/sy`, `drawCoverCaptions` spine `spineXPt/yCenterPt`,
front `startYPt/centerXPt`.
**Watch out for:** Cover `sections.back/spine/front.xMm` are CONTENT-relative (back=0,
spine=200, front=209). The section-background rect compositing IS correct to add
`COVER_BLEED_PX`. Don't unify the conventions without auditing all five sites.

### — CSV: style values normalised on parse — DONE
**Done:** `csv-to-template.js` now applies `.toLowerCase().replace(/-/g, '')` to
`caption_style` so `'Semi-Bold'` → `'semibold'`, `'Medium'` → `'medium'`. This is
what the engine + PDF style resolvers compare against. `lookupFont` in `export-pdf.js`
also normalises as a safety net.
**Watch out for:** Any caption_style value with internal capitalisation or hyphens is
now silently flattened. Don't introduce style values that need to preserve them.

### — PDF: EB Garamond family — static TTFs required — DONE
**Done:** `@pdf-lib/fontkit` (pdf-lib's stripped fork of fontkit) cannot decompress
woff2 — Brotli decompressor isn't included. Variable TTF (`EBGaramond-VariableFont_wght.ttf`)
can't be used either, because pdf-lib doesn't support variable font axes — it just embeds
the variable file at its default weight, so "regular" and "semibold" both render the same.
Fix: switched FONT_FILE_MAP to static TTF files (`EBGaramond-Regular.ttf`,
`EBGaramond-Italic.ttf`, `EBGaramond-SemiBold.ttf`). All sourced from Google Fonts
`static/` folder.
**Watch out for:** If a future font family is added, it MUST have static TTF or OTF per
weight needed. Variable fonts and woff2 are non-starters in this pipeline.

### — PDF: EB Garamond ligature gap workaround — DONE
**Done:** EB Garamond's GSUB ligature substitution (fi → fi-ligature glyph, etc.) hits a
`@pdf-lib/fontkit` bug — the ligature glyph's advance width is stored incorrectly in the
PDF's W array, producing a visible gap mid-word like "fi ne" or "f ine". Tried ZWNJ
(U+200C) injection between f and i — failed because @pdf-lib/fontkit has no glyph for ZWNJ
and substitutes a non-zero-width .notdef glyph. Real fix: draw each character as its own
`drawText` call. fontkit can't form a ligature across separate calls — no shaping context.
New helpers in `export-pdf.js`: `LIGATURE_FONTS` set + `measureNoLig()` + `drawTextNoLig()`,
applied at all four caption draw sites (slot, text panel, cover front, cover spine — spine
case rotates each character individually around its own origin, advancing cursor along Y).
**Watch out for:** Pair kerning is lost on EB Garamond (no "AV" tuck). Not perceptible at
16pt body text. If a future font is added to LIGATURE_FONTS, the per-character rotation
path in the spine case needs to be exercised.

### — SVGs already contain bleed artwork (discovered, NOT YET FIXED in PDF)
**Done:** Kseniia's design intent is for decorative artwork to extend past the content
edge into the bleed area. This is an insurance policy — the print machine may crop ±1mm
of the registered bleed line, so artwork pre-extended ensures the 200mm content area
prints clean regardless. Confirmed in cover SVG (`Back_BG_Color` rect at -18mm…200mm ×
-18mm…218mm; spine rect with full vertical bleed). Spread SVGs have clipping rects at
-3mm…203mm that permit decoration into bleed.
**Watch out for:** Current PDF script renders SVG with content-only viewBox and fills
bleed area with our own background-colour rectangles. This LOSES the SVG's bleed artwork.
Documented in LEARNINGS.md (2026-05-27 entry) and STATUS.md as the immediate next-session
task. The fix is to expand the SVG viewBox before rendering, render at bleed-inclusive
output size, and remove the duplicate back+spine section compositing on cover.

### Watch-outs for next session
- Engine renders content-only (200mm) and does not show bleed. That's correct/intentional.
  Don't try to add bleed display to the engine preview.
- When implementing the SVG-bleed fix, the cover compositing order changes (canvas bg =
  front colour, not back) AND the back+spine section rects must be removed (the SVG
  provides those with bleed). The front section rect stays.
- Photo MUST be composited BEFORE the SVG on cover (SVG decorations may intentionally
  overlay photos — z-index 2 in the engine confirms this).
- `csv-to-template.js` style normalisation affects all caption_style cells. Verify nothing
  downstream expects the original capitalised values.
