### Two products, one per paper stock
**Decided (owner):** Heirloom prints on offset (`aevia_hardcover_offset`), every other template
on matte (`aevia_hardcover_matte`). Both ids in `functions/.env` as
`PRINTSMARTER_PRODUCT_ID_HEIRLOOM` and `PRINTSMARTER_PRODUCT_ID`; **both required**, so a
half-filled env refuses to build a client rather than shipping one stock as the other.
`productIdFor()` chooses off the order's `templateName`, matching the lowercased `heirloom`
**prefix** so all four colourways resolve and a fifth needs no code change.
**Watch out for:** a missing `templateName` **throws** rather than defaulting to matte —
silently printing a Heirloom order on the wrong paper is a physical defect nothing downstream
would catch. This supersedes S185's single `aevia_hardcover` code.

### The address fallback — and the hole it turned out to close
**Verified before building** (`/verifying-claims`, against the code not memory): only two code
paths ever write `order.shippingAddress`, both in the payment flow — the saved-address copy in
`createCheckoutSession` (`index.js:1069`) and the Stripe webhook (`:1271`). So a staff test
order never paid through Stripe has none.
⚠ **My claim that a real paid order "never" lacks one was wrong.** That copy sits in a
`try/catch` that only warns, and its path **skips Stripe's address collection**, so the webhook
has nothing to fall back on; the guest path writes the field only `if (shippingAddress)`. Either
way the order reaches `paid` with no address and `submitPrintOrder` dead-ends, unfixable outside
the Firestore console.
**Built:** `submitPrintOrder` falls back to `customers/{email}.shippingAddress` — which is where
the checkout copy reads FROM, so in the failure case above it is the original, not a guess.
Precedence lives in a pure `resolveShippingAddress()` in `printsmarter.js` so it is **tested,
not mirrored**: the order's own address always wins, so the fallback can only fill an absent
field, never redirect a book that already has a destination. When it fires, the resolved address
is written onto the order so the record is truthful, and a line is logged.
**This replaces the Firestore hand-edit entirely** — owner and Xenia set an address once in
`pages/account.html` and every later test order resolves. ⚠ That form is gated on
`email_verified`; an unverified test account gets a 403.

### Dry run before submitting
`{ dryRun: true }` on `submitPrintOrder` runs every guard, the address resolution, the PDF
existence checks and the payload build, then returns `{ addressSource, payload }` **without
submitting**. Deliberately the same code path, not a parallel preview — a preview that
re-derives the payload can drift and show a book you are not ordering.
Dashboard "Preview submission" renders it; address and its source first (green = from the
order, amber = from the account, red = none), then product id, pages, price, PDF presence, and
the raw JSON collapsed.
⚠ **Not covered by any automated test** — the early return and the Firestore lookup need
Firebase, which the suite does not run. Verified by reading the code and driving the dashboard
against a stubbed response. The logic underneath IS tested via `resolveShippingAddress()`.

### 🔴 The first live dry run found a real defect: `"pages": "40"`
Orders store `pageCount` as a **string**; their example sends `"pages": 40` unquoted while
`"price"` IS a string, so they distinguish the types. Coerced at the payload boundary. Hidden
from 625 green tests because `PRICE_BY_PAGE_COUNT["40"]` resolves fine on a string key and the
fixture used a number — see LEARNINGS (S188).

### `shipping_code` was missing entirely
Their example carries `"shipping_code": "Standard"` and §5.4 records it closed with exactly two
values, but we sent none. Added as `Standard`: the docs never say it is required, so this is an
unknown, but the downside is asymmetric — an Express default costs money and a required field
missing means rejection.
**No `shipping_price`:** we charge none, and their docs describe `price` as feeding customs and
proforma documents, so inventing a figure would misstate one. Still open in the brief, along
with `return_address`.
