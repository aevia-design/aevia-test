## 2. The dependency rule was recorded wrong

The owner asked whether "no new dependencies" was a good call. It turned out **that rule does
not exist and never did.** The frontend already loads exifr, heic2any, Geoapify and the
Firebase SDK; six `package.json` files use npm freely. The real constraint is **delivery, not
dependency**: no build step, no npm on the frontend, libraries arrive as a `<script>` tag.
Reworded in `CLAUDE.md` and `AGENTS.md` — stated as a dependency ban it invites the opposite
failure, hand-rolling what a mature library already does.

Fell out of checking that: **TO-DOS #91** — those CDN script tags are unpinned and carry no
SRI hashes. Not urgent (waitlist-gated; cards are entered on Stripe's domain so it is not
skimming) but it should close before launch. Recommended fix is vendoring the four libraries
into `assets/js/`, which needs no build step.

## 3. Product fixes shipped

**#92 — `confirmUpload` errors reported as success** (`769b47e`). `fetch` only rejects on
network failure, so a 403/500 resolved and was never checked: the customer saw a success
screen while the order stranded at `uploading` with every photo already in GCS. Now checks
`res.ok` and retries 3× with 1s/3s backoff — safe because the handler is idempotent. On final
failure it still shows success (photos are up, the customer can do nothing) but posts to the
existing `reportUploadFailure` so staff get a trail. **Verified live:** AEV-078 came out
`status: new`, `uploadComplete: true`.

Severity was corrected down mid-task: the Firestore update runs *before* the email send, so
the likeliest 500 (SMTP) leaves the order correct and only loses the confirmation email.

**#93/F-P2-01/02 — non-photos accepted into the photo grid** (`39a15eb`). The
`accept=".jpg,…"` attribute only filters the OS picker; drag-and-drop walks past it, so a
`.txt` or `.pdf` was accepted, shown as a tile and **counted toward the required total**. And
`isImage()` matches on extension, so a text file renamed `.jpg` got in too. Two holes, two
checks: reject non-images up front, and reject anything that will not **decode**. The decode
result was already computed — it was warned to the console instead of acted on. Both report to
the customer; silently dropping files leaves them short with no explanation.

## 5. #88 closed — read this before reopening

Closed on the owner's call: Xenia had left the upload tab open a very long time, and a fresh
order completed normally. **Root cause never proven.** What this session established, most of
which contradicts the brief:

- **100% deterministic, not intermittent.** AEV-073/074/075/076 are each missing exactly
  `special_pages/fp4.png` and nothing else — four for four.
- **Template ruled out.** Papercut and Scribble emit the identical key through identical code.
- **The file was genuinely sent.** `photoManifest` is built from the client's `fileList`, so
  fp4 had a signed URL. Transport failure, not a dropped slot.
- **The diagnostics have never fired.** All five orders were created 2026-07-22 between 07:23
  and 08:59; `bde868b` shipped at 10:44 the same day. `uploadErrors: 0` is chronology.
- **Does not reproduce in Chromium** (AEV-080, Papercut, 50 files incl. fp4, clean).
- **Loose end:** a stale tab should hit whichever files are in flight, not the same slot four
  times out of four. Unexplained.
