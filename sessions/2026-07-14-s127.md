### THE BUG — promo payments were broken since S126

**Found:** `createCheckoutSession` (`functions/index.js`) always set
`allow_promotion_codes: false` on the Stripe session params, and ALSO set `sessionParams.discounts`
whenever a promo code was attached. Stripe rejects that combination outright —
`"You may only specify one of these parameters: allow_promotion_codes, discounts"` — so every
single payment that used a valid promo code 400'd at `createCheckoutSession` and silently fell
back to full price (the page's own error-handling, working as designed, just cleared the code
and let them pay full — so nothing looked broken from a casual glance, but no customer could
ever actually redeem a discount).

**Confirmed root cause directly against the Stripe API** (not just through the browser) before
touching any code — repro'd the exact error with a bare `stripe.checkout.sessions.create` call
carrying both params.

**Fix:** one line — `delete sessionParams.allow_promotion_codes;` right after
`sessionParams.discounts` is set. Re-verified the same way (raw Stripe call succeeds), then
`npm test` → 202/202. Owner deployed `functions:createCheckoutSession`; confirmed live —
checkout now shows the discounted total instantly instead of hanging for 90s before erroring.

**NOT COMMITTED.** The live Cloud Function now runs code that doesn't exist in git — `git diff`
still shows `functions/index.js` modified in the working tree. Commit this before it's lost or
before anyone rebuilds from `main` expecting the old (broken) behaviour.

### A known bug got in the way again — F-P1-01 (still open, not fixed this session)

verification, the "Refer a friend" panel showed a raw `"unverified"` error instead of minting a

around it by fully signing out and back in (mints a fresh token) rather than fixing the bug —
this is one of the small S3 code fixes already carried on STATUS.md, left alone per the owner's
"batch later" plan, not re-litigated here.
