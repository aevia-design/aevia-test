### 🔴 The first real `add_Order` failed — `Product not found. aevia_hardcover_matte`
**Attempted:** AEV-071 (40pp, matte) after AEV-100 was prepared. Their API returned
`HTTP 400 {"error":{"message":"Product not found. aevia_hardcover_matte"}}`.

**Nothing was consumed.** `submitOrder` throws before the Firestore update, so
`printsmarterOrderId` was never written and the status stayed `paid`. The once-only guard is
intact and both orders can be resubmitted unchanged once their side is fixed.

**What the failure proves works:** the request authenticated, reached them, was parsed, and
triggered a real product lookup that echoed our string back character for character. **Token,
customer id 3983, base URL, payload shape, JSON and the signed URLs are all correct.** The only
unresolved value is the one nobody can verify without a live call.

**Diagnosis — and a correction that matters.** Verifying against the repo alone (`/verifying-claims`)
produced the WRONG verdict: S185 records `aevia_hardcover` as issued by email, S186 records the
second id as still to be requested, and S188 records the two new ids as *"Decided (owner)"* —
a trail that reads as if we invented `aevia_hardcover_matte` / `_offset` and overwrote a working
id. **The owner's email says otherwise: Printsmarter issued both strings and RETIRED
`aevia_hardcover`.** The repo was missing the evidence, so the repo lost to the primary source.
Owner emailed them 2026-09-21 asking them to check the products are set up and assigned to
account 3983.
**Watch out for:** ⚠ **do not "fix" this by restoring `aevia_hardcover`** — it no longer exists.
⚠ **`functions/.env` is correct and must not be edited.** Verified: exact strings, no quotes, no
trailing whitespace.
⚠ **No test can catch a wrong product id** — `tests/printsmarter.test.js` feeds a fixture string
and asserts it arrives intact, so every value passes. Same shape as S188's `"pages": "40"`:
green suite, wrong value, only a live call exposes it.

**Corrected in four files** so the next session cannot repeat the mis-derivation: CLAUDE.md,
STATUS.md, `docs/briefs/printsmarter-api.md` §5 item 1, and S188's own log now all state that
**the ids were issued by Printsmarter** and that `aevia_hardcover` is retired.

### 🔴 "Mark approved for print" sat beside "Send to Printsmarter" and hid it — removed
**Found by owner**, mid-submission, by clicking it and believing the order had been sent.
`markSentToPrint` only flips `paid → sent_to_print`; it makes no API call. But because the
print-action row renders **only while status is `paid`**, the click **hid the button that
actually submits**, and the row then read **"Sent to print"** for an order that had never been
sent. Its confirm dialog also said "This cannot be undone."
**Fixed (`4c67f71`):** button removed. `submitPrintOrder` writes `sent_to_print` and
`printsmarterOrderId` itself on success, so the manual flip is redundant. The handler and its
endpoint stay as a console-only escape hatch, with a comment saying why it is unreferenced.
**Recovery, if it happens again:** set the status back to `paid`. The once-only guard is on
`printsmarterOrderId`, not on status, so nothing is burned.
**Tell the two states apart:** a real submission renders **"Sent to print · PS #<their id>"**.
Plain "Sent to print" with no number means it never went.

### ⚠ The send confirmation misreports the address — found, NOT fixed
The confirm dialog reads `order.shippingAddress` from the **locally loaded** order
(`dashboard.html:1038`) and shows **"⚠ NO SHIPPING ADDRESS ON ORDER"** whenever the address is
coming from S188's account fallback — which is exactly the case it was built for. Meanwhile
"Preview submission" shows the correct resolved address, because that runs server-side. Both are
literally true and they contradict each other on screen.
**Not fixed deliberately** — found mid-submission. The fix is to have the confirm call `dryRun`
first and show the **resolved** address plus its source, so the dialog and the preview can never
disagree. ~10 lines, no new code path.
**Why it matters:** this is the same class of defect as the button above. A last-chance warning
that cries wolf is worse than none, because you learn to click through it.

### Account name is editable (`c65adf9`)
**Built:** an inline Edit control on the Personal info panel writing Firebase Auth `displayName`
— the field signup sets and the rail, the panel and `order.html`'s prefill all read. Pure Auth
profile write: no Firestore, no function call, nothing to deploy beyond the page.
**Decided:** it deliberately does **not** touch `customers/{email}.shippingName`. A book can be
addressed to someone other than the account holder, so renaming an account must never redirect a
delivery.
**Verified:** module parses; driven in Chromium at 1280×900 and 390×844 — opens, hides Edit,
Cancel restores, no console errors. **The save itself was verified by the owner on the live rig**,
not by me (it needs a signed-in user).

### ⚠ An order's name does NOT follow the account name — and a real gap beside it
**Answered (owner asked):** the Printsmarter recipient comes from **`order.customerName`**, typed
into the order form at order time and frozen onto the order doc. The account `displayName` only
ever **prefilled** that box. Renaming an account changes nothing on existing orders, by design —
and S188's rule is that a fallback may **fill an absent field, never override a present one**.
**Fixed by hand:** owner corrected `customerName` on the test orders in the Firestore console
(`orders/{orderNumber}`, the document id **is** the order number).
**Found, NOT fixed:** `buildOrderPayload` ignores **`customers/{email}.shippingName`**, which
sits beside the `shippingAddress` the fallback DOES read. So when the fallback fires we ship to
the **account's address** under the **order's name** — two halves of one address from two
sources. No order has been submitted, so nothing has gone out wrong. The clean fix is to make the
name fall back exactly as the address does.
