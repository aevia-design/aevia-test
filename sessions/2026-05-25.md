### — captions_color column wired end-to-end
**Done:** Added `captions_color` CSV column → `parseCaptionStyle` reads hex or named color → serialized as `color: '#493955'` in template-data.js → `resolveColor()` in export-pdf.js handles both hex and named colors. All FP and Standard spread captions now use plum `#493955`.
**Watch out for:** `resolveColor()` falls back to near-black if the value is missing or unrecognised. `DATA.colors` lookup handles named colors — if a new named color is added to CSV, it must also exist in that map.

### — captions_alignment column wired end-to-end
**Done:** Added `captions_alignment` CSV column → `parseCaptionStyle` reads it as `align` → serialized in template-data.js → engine applies `captionEl.style.textAlign = cap.align || 'center'` → PDF `drawCaptions` uses `align` for x-position math (`left` = slot left edge, `right` = slot right edge minus text width, `center` = slot center minus half text width).
**Watch out for:** `upper-right` and `lower-right` positions are rendered in separate branches that compute their own x — the `align` field is only used in the `above`/`below` branch. Right-margin captions are always left-aligned by their x placement, not by the `align` value.

### — Style pills enabled for spread captions (Bug 4)
**Done:** Removed `if (_tbMode === 'spread') return;` early-return from `rebuildStylePills`. Pills (Regular/Bold/Italic/SemiBold) now render for all caption types including art gallery slots. `applyStyleToSpreadCapEl` now sets `fontWeight` and `fontStyle` on the DOM element so engine preview reflects selection. Pills write to `spreadCaptionStyles[si][side][slotIdx]` → read by `drawCaptions` in PDF via `scsOverrides[i]`.
**Watch out for:** B/I execCommand buttons remain — they add `<b>`/`<i>` HTML tags for inline word-level styling in the engine preview. PDF strips these via `stripHtml()`. Whole-caption style (weight/italic) must be set via the pills, not execCommand.

### — lower-right caption position corrected
**Decided:** `lower-right` = outside the photo in the right margin, bottom-aligned. NOT overlaid inside the photo.
**Why:** Earlier implementation placed caption inside the slot boundary (overlapping the photo). Correct behaviour mirrors `upper-right` (right-margin column) but anchored to the slot's bottom edge instead of top.
**Watch out for:** Engine: `capLeft = sLeft + sW + gap; capTop = sTop + sH - capH`. PDF: `x = BLEED_PT + slotRight + 2mm`, lines stack upward from slot bottom using `.slice().reverse()`.

### — upper-right missing from PDF drawCaptions (Bug 1)
**Done:** Added explicit `upper-right` case in `drawCaptions`. Previously `upper-right` had no case — fell into the `else` block and was treated as `below` (used slot bottom + offset as y-anchor). Fix: x = 2mm right of slot right edge, lines run downward from slot top.
**Watch out for:** The `if/else if/else` order in `drawCaptions` is now: `upper-right` → `lower-right` → `else (above/below)`. Do not collapse these back into a single else.

### — FP5 photos still missing after Bug 3 fix

**Done:** Found the real root cause. Engine save code always did `specialPhotos[key] = names[0]` — a plain string — for every key including FP5. Export code did `Array.isArray(artArr)` → false → null → no photo. Two fixes: (1) engine now saves FP5 as an array `["leftPhoto", "rightPhoto"]`; (2) export code has legacy string fallback (uses same photo for both pages).
**Watch out for:** Any existing `book-state.json` has `FP5: "art-1.jpg"` (string). The legacy fallback handles it — both art gallery pages get the same photo. Re-exporting from the engine saves the new array format. Session notes claiming "FP5 is stored as an array" were describing the in-memory `window.specialPhotos` structure, NOT the serialized JSON format — these differ.

### — B/I inline buttons removed from toolbar

**Decided:** Removed the B/I execCommand buttons entirely from the caption toolbar.
**Why:** `execCommand('bold/italic')` adds `<b>`/`<i>` HTML tags — visual-only in the engine preview. `stripHtml()` strips them before PDF drawing. They looked identical to the style pills, causing user confusion. Per-word bold/italic in PDF is not supported — whole-caption style via pills is the only PDF-affecting option.
**Watch out for:** Caption `innerHTML` may still contain `<b>`/`<i>` tags from before this change — `stripHtml()` handles them correctly. Do not re-add the B/I buttons.

### — FP5 art gallery photos not in PDF (Bug 3)
**Done:** `specialPhotos.FP5` is an array `[photo0, photo1]` (left=0, right=1), unlike other FP keys which are a single string. PDF export had `pool === 'artwork'` slots explicitly skipped ("Artwork slot — no photo"). Fixed `renderPage`: artwork slots now read `specialPhotos[spreadId][side==='left' ? 0 : 1]`. Fixed `pickVariantWithSpecial`: now handles array vs string for all FP types.
**Watch out for:** `pool === 'special'` (FP1/FP3/FP4) stores a single string or `{name}` object. `pool === 'artwork'` (FP5) stores an array. These are structurally different — do not unify them.

### — template-data.js renamed to scribble-data.js
**Decided:** Each template gets its own `<name>-data.js`. `template-data.js` implied it was the generic system file rather than Scribble-specific data.
**Why:** Prepares for multi-template scaling — pipeline code (engine, export script, csv generator) reads from the data file; new templates add a new file without touching the pipeline. Enforces the no-`if (template === 'scribble')` rule from LEARNINGS.md.
**Watch out for:** `.planning/` docs and `sessions/` logs still reference `template-data.js` — intentionally left as historical record. All live code and active docs (`CLAUDE.md`, `whats-next.md`, `customer-journey-v1.md`, `TO-DOS.md`) are updated.
