# Session 181 — 2026-08-17

Started from two screenshots the owner sent: Heirloom's cover and a text panel printed with
letters moved across the line break ("Anna & M / ichael", "…more t / han a simple hello.").
Owner suspected we'd fixed this shape of bug before and it had come back. Full
`systematic-debugging` pass, then `verifying-claims`, then `solutioning` for the fix itself.

---

## Root cause (verified by execution, not inspection)

The PDF was innocent. Ran its real `wrapText()` against the real IM FELL English font and the
real Heirloom box widths — it reproduces the engine's correct lines exactly, and its force-break
path can never split a completed word (verified by sweeping font sizes 50–100pt).

**The bad lines were stored in Firestore.** Since S159 the engine records where a caption broke
on screen (`captionVisualLines`) and the PDF draws those verbatim rather than re-wrapping — good,
because it guarantees print matches what staff approved. But the engine was saving **two
descriptions of one caption from two different sources**: the *text* (normalised on the way out —
`panelToPlain` strips `&nbsp;`) and the *line breaks* (measured off the raw, un-normalised DOM).
`applyTypographicRules()` had been quietly inserting non-breaking spaces for typographic polish
(after short prepositions/articles, plus one before the final word); with enough of them in a
caption, the browser ran out of legal wrap points and broke **mid-word**. That got recorded
faithfully by `captionVisualLines`, and the PDF drew it faithfully. Note: this NBSP polish never
reached print even before today — `stripHtml` already stripped `&nbsp;` — so it was purely
cosmetic and purely a print-time liability.

The existing guard (`linesMatchText`) should have caught this — it exists precisely to reject
stale line breaks — but it squashed all whitespace before comparing, and JS `\s` matches U+00A0
identically to a plain space. The one difference that mattered was invisible to the one check
built to catch it.

**Scope, checked by scanning all 90 Firestore orders** (only 7 have recorded lines at all — the
feature is young): exactly **one** order affected, AEV-099. The damage wasn't confined to text
panels — it hit two ordinary photo captions in the same order too. The mechanism itself lives in
shared engine/PDF code, not template data, so it isn't Heirloom-specific in principle — but
confidence that other templates are safe rests on n=1 in the wild, not a broader guarantee.

---

## The fix — two layers, by decision (`work/caption-line-integrity/decision.md`)

Considered: (1) make the DOM match the saved text — drop the typographic-rules function; (2)
make the saved text match the DOM — persist the non-breaking spaces and teach the PDF to honour
them. Chose (1): smaller change, and the feature being removed was already cosmetic-only in
print. Rejected repairing recorded lines in place without a structural fix — it patches
characters, not the break positions that actually printed wrong.

1. **`applyTypographicRules()` deleted from both engines** (staff + customer preview) — the
   caption DOM can no longer contain anything the saved text doesn't, so the two can't drift.
2. **`captionVisualLines()` normalises NBSP before measuring** — defence in depth: even an
   adversarial DOM state (every space forced non-breaking, the exact condition that broke
   AEV-099) now records correct word-boundary breaks. Verified live in the engine against that
   worst case.
3. **`linesMatchText()` tightened** from "same characters, whitespace squashed" to "the lines
   REJOIN into the exact saved text" (hyphen/dash breaks excepted, since those rejoin with no
   space). This is what repairs AEV-099 **without a re-save** — the next render will reject its
   stored lines and fall back to the PDF's own (verified-correct) wrapper.
4. Recorded lines that do pass the check are now stripped of any surviving NBSP before drawing —
   the print fonts have no glyph for it and would draw a `.notdef` box (same failure class as the
   Wander "WILD" bug).

  any diff touching `order.html`'s dependency surface, not because that file changed).

  browser state that no longer exists; the fix makes it unreachable either way, so this is
