### ADR-0008 BUILT — promo entry moved off Stripe's hosted checkout

**Done:** Four pieces.
- `functions/promo-utils.js` (NEW, pure) — `normalizePromoCode`, `promoValidationDecision`,
  `describeDiscount`. No Stripe/Firebase, so it unit-tests.
- `tests/promo.test.js` (NEW) — 16 tests; suite **202/202**.
- `functions/index.js` — shared `resolvePromo(db, code, order, orderNumber)` (Stripe lookup →
  `referralCodes/{id}` owner lookup → decision; `console.warn`s a denied self-referral so
  attempts are traceable) + **NEW `validatePromoCode` Cloud Fn** (token-gated, returns
  `{valid, reason, message}`). `createCheckoutSession` now takes `promoCode`, **re-validates it
  server-side**, attaches `discounts:[{promotion_code}]`, and sets
  **`allow_promotion_codes: false`**.
- `pages/customer-preview.html` — "Have a code?" field + Apply beside Pay now, shown only in the
  approved-unpaid state. Copy stop-slopped.

**Why the server re-validates:** the page's "this code is valid" claim is not proof. A
hand-crafted POST straight to `createCheckoutSession` would otherwise skip the self-referral
block entirely. The check has to live in the money path.

**Watch out for:** `allow_promotion_codes` is now **false on every order** — our field is the ONLY
way to redeem a code. If `validatePromoCode` is down, nobody can use a promo (they can still pay
full price). Accepted cost, named in the ADR.

**Watch out for:** if Stripe rejects a code at session-create (a restriction we don't model —
minimum amount, currency, product scope), `createCheckoutSession` returns 400 with
`reason: 'promo_rejected'`; the page clears the code and lets them pay full price. It never
silently drops the discount and charges anyway.
