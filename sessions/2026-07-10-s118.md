## What shipped

### 1. Referral: first-order-only, Stripe ↔ DB consistent (`c77c528`, NOT deployed)
**Problem (owner's question):** a referral code worked even for a customer who already had orders — Evgeny wants it to apply only on an account's *first* paid order, and Stripe + our order DB to agree.

**Root cause:** `createCheckoutSession` never attached a Stripe Customer, so the share code's `first_time_transaction: true` restriction had no customer history to check and never bound. Guest checkouts = anonymous one-off payments.

**Fix (via `/solutioning`, option A of three):**
- `functions/index.js` `createCheckoutSession` — find-or-create a Stripe Customer keyed by `normalizeEmail(order.email)`, cache the id at `customers/{email}.stripeCustomerId`, and pass `sessionParams.customer`. Folded into the existing customer-doc read (one lookup). Now Stripe rejects the code on a 2nd+ paid order, at the payment page.
- DB-side guard so the two systems actively agree: new `countPriorPaidOrders(db, email, excludeOrderNumber)` (queries by email like `getMyOrders`, filters `status==='paid'` in code — no composite index) + a new `refereePriorPaidOrders` input/rule in `referrerRewardDecision` (`functions/referral-utils.js`, reason `referee_not_first`). `handleReferralReward` only runs the count when a real referral code was used.
- `tests/referral.test.js` — 3 new tests (referee_not_first; still-issues at 0; self-referral precedence). 186/186.

**Accepted edge:** a customer who ordered as a *guest before this deploy* has no Stripe Customer yet, so their next order still looks "first" to Stripe. Bounded €10; the DB guard catches it on the reward side. Pre-deploy orders are all test orders.

### 2. Instruction bar centred (`a643eb1`)
Owner reported the customer-preview tip bar wrapping to "2 ugly lines" in Safari. **Measured it in both engines** (Playwright WebKit + Chromium): the six tips total ~1580px and overflow any laptop viewport in *every* browser — WebKit needs 1579px, Chromium 1580px (1px apart). Not a Safari bug; the owner's Chrome was just on a wider display. Fix: `text-align:center` + `line-height` on `.edit-hint` so it wraps to two balanced centred lines, identical everywhere.

### 3. Responsive: book scales to fit + bar never overlaps (`e9484c1`, customer-preview only)
Owner's live-Safari test surfaced two more bugs (both fixed-pixel-assumption root cause):
- **Book didn't fit narrow windows.** Only the cover auto-scaled (`fitCover`); interior spreads were locked at 1204px and overflowed. Generalised `fitCover` → `fitBook`: wrap each spread in a new `.spread-scale-wrap`, give `.spread-pages` a fixed `width:1204px`, scale it by `min(1, avail/1204)`, and collapse the wrapper height to `600*scale` (else empty vertical gaps). Removed the viewport-keyed `@media (max-width:1399px)` stacking query (scaling supersedes it). Preview mode centres via `transform-origin:top center` + `margin:0 auto`; edit mode stays top-left to line up with the sidebar.
- **Instruction bar overlapped the first spread header.** Clearance was a hardcoded one-line reserve (`padding-top: calc(69px+53px)`). New `adjustHintReserve()` measures the bar height live and sets `page-body` padding to `69 + hint.offsetHeight + 8`; clears any wrap count. Kept `position:fixed` (chose the critic's lower-risk JS-measured reserve over sticky).
- **Reposition drag broke under scale (critic HIGH).** `attachCropDrag` measured pointer movement in screen px but divided by `clientWidth` (layout px) — only agree at scale ≈1, which is why the barely-scaled cover *looked* fine. On a scaled spread the photo would track at the wrong gain. Fix: `dispScale = getBoundingClientRect().width / clientWidth`, divide the delta by it. Fixes spreads AND a latent cover bug. **Swap-drag and caption edit verified unaffected** (native DnD / contenteditable don't use this maths).
