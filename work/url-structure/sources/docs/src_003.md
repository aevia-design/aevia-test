# Cool URIs Don't Change

Source: https://www.w3.org/Provider/Style/URI
Author: Tim Berners-Lee
Publisher: W3C
Original date: 1998 (maintained/referenced by W3C since)
Retrieved: 2026-09-23 via WebFetch (summarized extract)

## Main Argument

Berners-Lee argues webmasters bear responsibility for creating stable, persistent URIs: "It is the duty of a Webmaster to allocate URIs which you will be able to stand by in 2 years, in 20 years, in 200 years." Core principle: "A cool URI is one which does not change."

## Why URIs Break

Most URI failures stem from organizational choices, not technical necessity:
- Reorganizing websites without maintaining old URIs through redirects
- Exposing implementation details (file locations, software mechanisms)
- Including author names or organizational roles in paths
- Embedding status indicators like "draft" or "old"
- Using file extensions like ".cgi" or ".html"

## What Should NOT Be Included in URIs

"Designing mostly means leaving information out." Avoid:
- Unstable identifiers: author names, subject classifications, status designations, access levels, software mechanisms (e.g. "cgi-bin", ".pl")
- Organizational structures reflecting server divisions (expose infrastructure that inevitably changes)
- File extensions (commit you to formats you may abandon)

## URI Structuring for Longevity

Optimal approach uses creation dates as stable anchors, e.g. `http://www.w3.org/1998/12/01/chairs`. Use content negotiation to serve files without exposing extensions; avoid hierarchical topic-based classification schemes. "Many, many things can change and your URIs can and should stay the same."
